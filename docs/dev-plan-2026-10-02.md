## 一、本轮修复的四个缺陷

前一轮的结论是：这个项目的失败模式不是「写错了」，而是**「看起来是对的」**——代码能编译、测试能过、TODO 能勾选，但生产路径上从未生效。本轮四项修复全部属于这一类。

| # | 位置 | 缺陷 | 表现形式 |
|---|------|------|---------|
| 1 | `sisyphus-metrics/src/observability.rs` | 6 个 span 用例依赖进程级全局 tracing 订阅者 | 单独跑 `cargo test -p sisyphus-metrics` 全失败，混在全量里全绿 |
| 2 | `sisyphus-bridge/src/peer/manager.rs` | 入站与出站共用一个事件通道 | 回弹只能靠解析主键的约定终止，全连接集群下 O(N²) 重复投递 |
| 3 | `sisyphus-bridge/src/peer/experience_sync.rs` | handler 不持有 `PeerManager`，通道随时可关 | 调用方一处没持有就静默退出，进程还活着但同步已死 |
| 4 | `sisyphus-mem/src/experience_bank.rs` | 重启后本地序号归零 | 比主键碰撞更隐蔽：丢的是**刚发生**的最新经验 |

### 1.1 覆盖率是假的

`observability.rs` 里 6 个用例断言 `span.metadata()`。该方法依赖当前 dispatcher：进程内没有任何订阅者时 `tracing` 直接返回 `Span::none()`。这些用例原先能过，纯粹因为同一进程的别的测试恰好装上了全局订阅者。

这与第一轮挖出的 `sisyphus-mem/src/tests.rs`（227 行、7 个用例从未被 `mod` 引入）是同一类问题：**测试存在 ≠ 测试在跑**。区别只在于孤儿文件是显性的，而「依赖全局状态」是隐性的——它不报错，只在单独运行时暴露。

修法是 `tracing::subscriber::with_default`（线程局部）而非 `set_global_default`（进程全局、只能成功一次）。后者需要 `Once` 串行化，且与其他测试争抢同一个全局槽位；前者并行执行也互不干扰。

### 1.2 让「不回弹」成为结构保证

事件要到达对端，必须经由拨号器把本地事件写进 gRPC 流。而入站事件（从远端收到的）此前也写进了**同一个** `event_tx`，于是被拨号器当作本地事件再发给所有 peer。

回弹不会无限持续，靠的是 `ExperienceSyncHandler` 里的自过滤：解析主键取出来源节点，与自己相同就丢弃。这条约定有三处脆弱：

1. `experience_origin_from_key` 在主键不符合 `exp:{ts}:{origin}:{counter}` 时返回 `None`，此时 `== Some(self_node_id)` 为假，**事件照单全收**；
2. 终止条件依赖每个接收端都正确实现过滤——任何一端漏实现就形成环；
3. 全连接 N 节点集群下，同一条经验被投递 O(N²) 次。

修法是拆成两条通道：

- `event_tx`：**本地产生**，拨号器与服务端 `Stream` 订阅，唯一的出口。
- `inbound_tx`：**远端收到**，只有 `ExperienceSyncHandler` 订阅，拨号器不订阅。

`ExperienceSyncHandler` 改订阅 `inbound_tx`。副作用是正向的：本地经验已经由 `PeerBroadcastExperienceBank` 直接落库，handler 再经 CRDT 合并走一遍本就是多余的，现在它连看都看不到了。

自过滤保留，但语义变了——从「终止回弹的唯一机制」降级为「防御对端回送」。注释同步改写，不再声称它承担了它并不承担的职责。

**行为变更（重要）**：分离后，节点不再转发收到的经验，即**跨节点不再有传递性 gossip**。3 节点全连接下 A 收到 C 的经验后不会再转给 B。这是有意为之——转发是此前通道混用的意外产物，而 ADR-010 的直接反熵才是收敛的正道。但这也意味着：**在 ADR-010 落地前，部分互联的集群会持有不一致的经验视图**。这是本轮引入的已知局限，已记入遗留清单。

### 1.3 关闭语义：从「碰巧没人会这么用」到结构上不可能

`broadcast::Receiver` 不会让通道保持存活，只有 `Sender` 存活才不会收到 `Closed`。原实现里 `self.peer_manager` 只在调用 `subscribe()` 时借用一下就被丢弃——于是只要调用方别处没有持有 `PeerManager`，接收端立刻在 `select!` 里静默退出。

生产代码目前显式持有一个 sender 兜底，所以没暴露。但兜底在调用方，不在接口里：这是个「碰巧没人会这么用」的约定，测试已经踩过一次（接收端一起来就死）。

修法是让 handler 任务全程持有 `Arc<PeerManager>`——Sender 的存活由类型系统保证。同时把 `Closed` 分支从 `warn!` 提到 `error!`：任务自己持有管理器，正常情况下不可能走到那里，真走到了就是拓扑被拆掉，不该只是记一条警告。

### 1.4 序号恢复：比主键碰撞更严重的后果

第一轮修 P1 时把本地序号从「每次都传空时钟导致恒为 1」改成实例级 `AtomicU64` 单调递增，并在文档里记下「已知局限：进程重启后序号归零」。

当时记录的局限是主键碰撞——重启前后落在同一秒才会撞。但继续追下去会发现真正的后果在别处：

```rust
if exp.version < counter {
    exp.version = counter;
}
```

`counter` 同时就是写入的 `version`。序号归零意味着重启后新写入的 `version` 从 1 重新开始，而对端可能已经持有本节点 `version=500` 的经验。CRDT 版本裁决会把这些**刚发生的**写入判为旧版本而拒绝——经验凭空消失，且**不产生任何错误**。

主键碰撞会抛 INSERT 错误（第一轮里 `execute_and_record` 吞掉了它）；version 回退则一路静默，丢掉的是最新的数据。

修法：`VectorExperienceBank::new` 启动时从存储层读回本节点已用掉的最大计数。`MfsStore::max_local_counter` 按 `id` 解析 `origin` 与 `counter` 后过滤，只统计本节点自己写的行——远程合并进来的行 origin 不同，不会干扰。P1 之前遗留的旧格式主键解析不出 counter，跳过即可。

节点 ID 的解析被提取为 `local_node_id()`：构造时（用于恢复）与写入时（用于生成主键）读的是同一个值。若两处读到不同结果，恢复出的序号会被算到错误的 origin 上，等同于没恢复。

恢复失败不阻止启动，退化为从 0 开始（与修复前一致），但打 `warn!`——**静默退回到有缺陷的模式是最坏的退路**。

## 二、后续开发计划

### 阶段 C：反熵补偿落地（ADR-010，最高优先，2-3 天）

当前集群**没有收敛机制**。经验同步是即发即失的：事件在建流之前发出去就永久丢失，断线期间的经验在重连后不会补回，新节点加入时对既有经验一无所知。这不是 bug，是协议本身的缺口——第一轮打通的是「链路通」，不是「数据全」。

ADR-010 已给出协议（dial 方发版本向量、peer 回送差量、分页有界，挂在现有双向 `Stream` 上不新增 RPC），本轮的前置缺陷 P1 与序号恢复都已让它成立。剩余：

- [ ] **启动时全量 sync**：新节点 Join 后向 peer 拉取既有经验
- [ ] **断线补偿**：重连后按 vector clock 差量补齐
- [ ] **版本向量导出接口**：`ExperienceBank` 需要能回答「我有什么」而不只是「我写了什么」
- [ ] **分页与边界**：差量应答必须有界，否则大库会让单条 gRPC 消息超出限制

前置：阶段 C 完成后，1.2 节引入的「不再传递性 gossip」才算真正有替代方案。

  收工：15 条里大量条目的**期望值本身也带着旧实现的偏见**，等于用
  旧实现的漏报面去定义「正确」。故又把这 15 条喂回旧实现（`4c99c06`）
  逐一对照，取得可复现的证据：**旧实现 15 条错 6 条，且 6 条全是漏报**
  （判「豁免」而实际该报），新实现 15 条全对。

      清理早于 set_var                        期望报出  旧豁免 ❌
      remove_var 变量名不同                  期望报出  旧豁免 ❌
      两次 set_var 仅一次清理                期望报出  旧豁免 ❌
      闭包内 set_var、外层清理                期望报出  旧豁免 ❌
      move 闭包 |x| 内 set_var、外层清理     期望报出  旧豁免 ❌
      外层 set_var、闭包内清理                期望报出  旧豁免 ❌

  这 6 条收敛到 **4 处根因**（同一判据的多个漏报面，故「6 条失效」与
  「4 处修复」两个数字都对，但混用会自相矛盾）：

  1. **`protected` 判定只看 barrier，从不比对变量名**：
        set_var("K", …); remove_var("OTHER"); assert!(…);
     被当成「K 已清理」而豁免。讽刺的是「按变量名匹配」这个判据在
     守卫那侧**早就实现了**，remove 侧却一直只看文本——同一个概念存
     在两套标准。上一轮已为守卫侧写过这条教训，这里重蹈。教训写在注
     释里不够，得落在**每一处**同类判定上。

  2. **`protected` 不要求清理在本次 `set_var` 之后**：
        remove_var("K"); set_var("K", …); assert!(…);
     被豁免——清理早已跑完，这次设值没人管。

  3. **`protected` 的候选清理跨出当前函数**：`REMOVE_VAR_RE` 在**全文件**
     上搜索，再用 `enclosing_fn` 过滤出同名函数——过滤只保证「在同一个
     函数里」，却把**位置**交给了 `r_body.find(r.group(0))` 这个文本查找。
     `group(0)` 恒为 `"env::remove_var("`，于是「同函数里第一处 remove_var」
     的位置被拿来给**每一处** remove_var 判断 barrier 先后：
       - A/B 交替、B 未清理 → 借了 A 的清理位置，误判为已保护；
       - 同函数两处相同文本 → 第二次仍命中第一次的位置。
     真正的位置本就在 match 对象里（`r.start()`），绕道文本查找把两个
     都丢了。这是**独立于缺陷 1、2 的第三个漏报面**，已单独实测确认
     （「A/B 交替、B 未清理」旧实现豁免、新实现报出）。

  4. **闭包边界完全缺失**。`enclosing_fn` 只认 `fn`，于是闭包体内的
     语句被归到外层函数，外层的 `remove_var` 被当成了闭包内 `set_var`
     的清理。但两者根本不同时执行：闭包体在 `f` 被调用时才跑，外层
     那句在定义处就跑完了。新增 `_pos_in_closure()` 判闭包归属。

  闭包判定本身又踩了三个坑，每个都是「看似实现、实则恒失效」：

  - **方向写反**：从 `{` 往回扫，把遇到的第一个 `;` 当作「已离开表达
    式」。但 `let f = || { … };` 里的 `;` 在闭包**之后**，扫到的是上
    一条语句的分号，于是闭包体永远被判成普通块。正确做法是**向前**找
    收尾竖线，`;` 只能作为「配对竖线之前不得出现」的禁字符。
  - **只看最深那层**：`|| { unsafe { set_var(..) } }` 里最深是
    `unsafe` 块的 `{`，闭包体是上一层。必须整条链都判。
  - **修饰符块入栈出栈不成对**：`unsafe {` 不开启作用域（表达式修饰
    符而非块语句），我让它跳过入栈，却照常弹栈——每遇一个 unsafe 块
    就多弹一次，把闭包体和函数体一并弹掉。实测闭包内「成对」那条用例
    的块链被弹成 `[函数体]`，闭包体凭空消失。改为整块跳过。

  **一条「变异没被抓住」的正确处置**：想用变异验证第二道配对检查
  （闭包竖线是否成对），去掉它后自检全绿。我花了多轮试图构造能区分的
  用例，最后查清原因：**该检查在合法 Rust 上不可达**——凡 `|` 紧邻
  `{` 的合法语法只有闭包，match 的 or-pattern 是 `A | B => {`，紧邻
  `{` 的是 `>`，第一道检查就拦下了。这不是「漏网的失效」，而是防御
  非 Rust 文件与未来语法扩展的冗余代码。已在注释里写明，免得下次变异
  验证再次把它当成待查的失效。

  **第四轮：扫描范围的盲区**。前三轮都在抠**判据算得对不对**，这一轮
  才问一个更靠前的问题：**门禁扫的是不是所有该扫的代码**。前几轮全部
  漏掉了这一层——判据在 `crates/` 里算得再准，`ide/` 里的泄漏照样
  零报出。

  实测 `SCAN_DIRS = ("crates", "webui", "evals")` 漏掉 `ide/`（10 个
  `.rs`）与 `tools/`（1 个）。探针证实：往 `ide/` 放一个含裸
  `set_var` 的文件，`scan()` 报 0 条；把 `ide` 加进清单后报 1 条。
  当前这两个目录里恰好没有真实泄漏——但那是**运气，不是门禁**。

  这与前三轮是同一个失效模式，只是位置更上游：硬编码的清单不会随仓库
  生长而更新，且症状是零。改为 `_scan_dirs()` 自动发现「顶层含 `.rs`
  的目录」，并显式排除产物/工具目录。方向上的不对称仍是刻意的：自动
  发现的代价是多扫几个无害目录（最多报噪音），硬编码的代价是新目录
  一出现就静默漏扫。

  刻意**没有**改用 `git ls-files`：那会漏掉未提交的新文件，而新文件
  恰恰是泄漏最常被引入的地方——门禁得管住的是工作区，不是提交。

  配套修掉两处连带问题：

  - 端到端用例的探针目录原本叫 `crates`，且恢复时把 `SCAN_DIRS` 写
    回旧值。**这等于把刚修掉的 bug 复制进自检的恢复路径**——写死清单
    时自检照样全绿。已改为 `selfcheck_probe_dir`，并不再改写
    `SCAN_DIRS`。
  - `_self_check()` 原用 `globals()["ROOT"] = …` 临时换根目录。换成模块
    属性赋值后 `ROOT` 被 Python 当作局部变量，直接抛
    `UnboundLocalError`。已加 `global ROOT`（必须在函数体开头，不能在
    `try` 块内，否则报 `used prior to global declaration`）。

  变异验证（两种失效都会触发同一条用例，故提示文案必须同时写出两个
  可能，否则会照着错误方向查）：

  | 变异 | 结果 |
  |------|------|
  | 退回硬编码目录清单 | exit 2 ✅ 抓住 |
  | 加回文件级 `impl Drop` 跳过 | exit 2 ✅ 抓住 |

  耗时实测：`_scan_dirs()` 单次 0.003s，全量 `scan()` 4.4s，无可感知
  代价。

  **第五轮：文档承诺与实现对不上**。前三轮修判据、第四轮修扫描范围，这一
  轮换了个角度：**先读门禁自己声明的边界，再逐条去代码里核实它是否成立**。
  结果是文件头部那份「刻意不判定」清单里，**两条承诺实现里根本没有**：

  | 文档曾写 | 实现实测 |
  |---------|---------|
  | 「刻意不判定 `set_var` 出现在**生产代码**里」 | 判定照做：生产函数里 `set_var` 无清理 → **报出 1 条** |
  | 「纯串行测试二进制（`tests/` 下）里的 `set_var`」不判定 | 实现里**没有任何按路径的豁免**；实测在 `crates/sisyphus-mem/tests/` 下放一个裸 `set_var` → **报出 1 条** |

  两条都是**实现更严、文档更松**。这比反过来危险得多：文档说「这里不管」，
  下一个人就会放心在那里写裸 `set_var`，而门禁其实会报——他要么被莫名
  的噪音困扰后把门禁关掉，要么去代码里找一条根本不存在的豁免。两样都是
  坏结果。

  处理方式：**保留更严的实现，改文档**。理由是生产代码里的裸 `set_var`
  同样污染进程环境（真正的配置覆盖应走 `Config` 而非直接改环境变量）；
  `tests/` 下虽然每个文件独立进程，但「裸 `set_var` + 断言失败即残留」
  仍该修。当前 `tests/` 下没有任何真实 `set_var`（`snapshot_writeop.rs`
  里的 `write_op_set_var` 只是枚举变体名，不是环境变量写入），所以这两条
  承诺从未被兑现过、也没造成过噪音——**靠的是运气，不是设计**。

  配套把真实行为钉进自检（新增 2 条用例，用 `pub fn` 形态以保留「这是
  生产代码」的意图）。变异验证：在 `check_panic_safe_cleanup` 里注入
  「`pub fn` 内豁免」→ 自检 exit 2 并准确指出是「刻意不判定清单与实现
  脱节」。若不钉住，下次改文档时又会漂回去。

  顺带核实了几处**确实成立**的边界，免得为了找问题而误伤：

  - `SET_VAR_RE` / `REMOVE_VAR_RE` 要求字面 `env::` 前缀。全仓 `set_var`
    子串共 15 处：真实调用 `std::env::set_var` 9 处（全命中）、注释文字里
    5 处（分布在 4 个文件的 6 行上，其中 `mod.rs:787` 那行含两次）、枚举
    变体名 `write_op_set_var` 1 处。**无点号形式 `env.set_var`**，正则够用。
  - 生产路径的 `set_var` 只有守卫实现文件 3 处（第 74/93/149 行），已豁免。
  - `OnceLock` 17 处全是「一次性初始化只读数据」或 `OnceLock<Mutex<()>>`
    串行门闩，**不是可被测试改写的状态**，门禁不管是对的。`static mut`
    0 处。子进程 `Command::env` 只影响子进程、不污染本进程，不算漏报。

  这一轮的教训与前几轮同源，但角度不同：**门禁的说明文字也是需要验证
  的对象**。前四轮验证的是「判据算得对不对」「扫得全不全」，这轮才发现
  还有一层「声明的边界是不是真的」。三层里最容易被忽略的恰恰是最后一层
  ——因为它不影响任何一次运行结果，只影响下一个人会不会误信。

  第三轮那条教训仍然成立：**判据自检本身也可能「看起来在跑」**。
  探针集的价值不在于每次都找出新缺陷（它已固化进自检），而在于强制对
  每条用例回答「为什么该报/该豁免」——本轮当场那条期望值写反就是这么
  发现的。但更刺痛的一条是**「当场只错 1 条」这件事本身**：它看起来像
  一次干净的验证，实际却掩盖了 6 条漏报，因为 15 条用例里有相当一部分
  是**照着旧实现的行为写的期望值**。用被判据自身定义「正确」，判据就
  永远自洽、永远绿。真正闭合的做法是把用例喂回旧实现对照，逼出「这条
  是我认定的语义，还是旧实现碰巧的行为」——本轮那 6 条全在这一步才暴露。

  另一处门禁自身的缺陷也在本轮修掉：`audit_ignored.py` 会把字符串字面量
  内部的 `#[ignore]` 当成真实属性，判成「裸 `#[ignore]` 无理由」，使
  `make audit` 长期失败（`crates/sisyphus-tools-system/src/web.rs:498/508`
  的 `.expect("...已显式 #[ignore]...")`）。**不是 `web.rs` 有缺陷。**
  修法是扫描阶段记录字面量区间供 `scan()` 判定，而不是剥离内容——属性
  `#[ignore = "理由"]` 的理由本身就在字符串里，剥掉会把 24 处合法理由一
  并抹掉（实测全部误报）。变异验证：改裸 `#[ignore]` 必被抓；字符串内
  `#[ignore = "..."]` 必被跳过且总条目数恒为 24。

## 三、遗留问题（本轮引入或仍未处理）

1. **不再有传递性 gossip**（本轮引入）：入站事件不再转发。ADR-010 落地前，部分互联的集群会持有不一致视图。见 1.2 节。
2. **`StateProposal` 仍无消费方**：`ClusterConsensus` 有实现但没人调用，事件被丢弃。属阶段 9 后续，不是缺陷。
3. **旧格式主键待决**：P1 修复前的存量行保留旧主键。`max_local_counter` 会跳过它们（解析不出 counter），因此它们既不参与序号恢复，也不会被新逻辑误判。0.x 清库重建即可，无需写迁移。
4. **序号恢复是 O(N) 全表扫描**：`SELECT id FROM experiences` 后在 Rust 侧过滤。只在启动时执行一次，当前量级下可接受。若经验库增长到十万级，应改为 `id LIKE 'exp:%:{origin}:%'` 下推过滤——注意 `LIKE` 中 `%`/`_` 需转义（node_id 来自环境变量）。
5. **`StateProposal` 与 `ExperienceSync` 的容量独立**：两条通道各自 256。订阅者落后会丢事件，且经验同步丢事件不可恢复——这正是阶段 C 反熵要解决的问题。

   的 `[[bin]] path = "runner.rs"` 把 `.rs` 挂在顶层 → 一度把 5 个正常文件
   报成孤儿；
2. 「顺手」把 `tests/` 也纳入候选 → **191 个误报**。`tests/` 下每个 `.rs`
   本来就是 Cargo 自动编译的独立目标，不需要 `mod` 声明；
3. `ROOT.glob("**/Cargo.toml")` 匹配到**仓库根自己的**虚拟 workspace 清单
   → ROOT 成为 crate 目录，所有散落 `.rs` 都「属于某个 crate」，
   `tools/dummy_tool.rs` 反而又漏了。

第 3 条是这次最值得记的：判据从「按目录名列举」改成「按 Cargo 事实判断」之
后，第一版把根清单当成了 crate，于是修复动作自身把要修的问题盖住了。

**两个门禁都补了 `_self_check()`**，且都遵循同一条规则：**自检必须直接调用
生产函数**。最初给孤儿门禁写的是「另抄一份可测版本」，自检绿灯而生产代码里
的缺陷照样存在——副本与正本会漂移，这恰恰是自检最危险的失败模式：它给了安
全感却没给保护。发现后重构成 `_workspace_crates(root)` / `_candidate_files()`
由 `main()` 与自检共用。

`audit_ignored.py` 的自检补了 5 条变异才全部抓住，其中三条值得记：

| 变异 | 旧自检 | 加强后 |
|------|--------|--------|
| 不识别 raw string | ✅ 已抓（但计数碰巧相同，见下） | exit 2 |
| `_real_ignores` 忽略 spans | **全绿**（真实扫描 24 → 26 处误报） | exit 2 |
| 剥离吞掉换行 | **全绿** | exit 2 |
| 不处理 `\"` 转义 | **全绿** | exit 2 |
| 不识别结束引号 | **全绿** | exit 2 |

「不识别 raw string」这条特别有意思：旧自检只断言最终计数，而把 raw string
分支短路后**计数仍是 0**——因为 `r` 后的 `"` 照样被当普通字符串跳过，结果碰
巧一致。计数对了不等于走对了分支。补的断言检查的是分隔符本身。

顺带发现并删掉一段**死代码**：`_blank()` 里那层「跳过换行以保行号」判断在
任何场景下都不会生效——行注释传的区间止于换行之前，块注释止于 `*/` 之后，
真正的换行由主循环自己 append。实测把该判断改成恒真，换行数仍是 3。它骗过了
两条本想保护它的断言。留着它只会让人误以为「这里有保行号逻辑，改动时要小
心」。

### 第七轮：把「声称可用于 CI、实际未接入」的工具补上接线

前六轮都在加固门禁**判据本身是否正确**。第七轮换个角度：不看判据对不对，
而看**工具是否真的接在它声称的地方**。

`scripts/scan_flaky.py` 有完整的 Makefile 入口（`make scan-flaky`）、有退出码
设计、有 20 行注释记录踩过的坑，但它**从未被任何 workflow 调用过**——而它
自己的文档写着「便于 CI 定期拦截」。承诺与实现脱节，且这种脱节不会以任何形式
报警：工具能跑、文档没错、CI 也不会红。

先核实脚本本身是否健全（避免把问题归错地方）：

| 检查项 | 结果 |
|--------|------|
| 零产物时的退出码 | `return 2`（`if not binaries` 分支），非 0 ✅ |
| 全部产物过期时 | 同样落到 `return 2`，不静默返回空 ✅ |
| 本机 20 个可扫 crate 的产物新鲜度 | 20/20 均有效，无部分静默漏扫 |
| 二进制名哈希位数 | 16 位十六进制，与正则一致 |

脚本本身没有缺陷，缺的只是接线。接入方式的选择基于两条实测：

1. **成本**。快 crate 单轮 0.21 / 1.64 / 1.97 秒，20 crate × 16 轮即使用

2. **它检测的东西在受控 runner 上本来就难复现**。它针对的三处真实缺陷失败率
   低至 1/16，而 GitHub runner 负载稳定，恰是低频竞态最难撞见的环境。

因此**刻意不挂 PR 门禁**：付 1.7 分钟却大概率扫不出东西，只是在稳定环境里
制造「扫过了所以安全」的安全感，比不扫更糟。改为独立的 `schedule` +

### 第八轮：workflow 里让 CI 静默失效的引用错误

第七轮查的是「工具没接在它声称的地方」。第八轮把范围扩到 workflow 内部，
找**引用写错但不报警**的地方——这类缺陷的共同点是：CI 全绿，坏消息只出现在
你恰好去读渲染结果的时候。

先用一次性脚本扫全仓，捞出两处：

**一、`ci.yml` 引用了未声明 `id` 的 step**

PR 评论原文：

```
📊 **Bench Dashboard** ([详情](${{ steps.upload-artifact.outputs.artifact-url }}))
跑 ${{ steps.upload-artifact.outputs.artifact-size }} 大小
```

`upload-artifact` 那个 step 从未声明 `id`，而 GitHub 只为显式声明 id 的 step
暴露 outputs。两处引用**静默展开成空字符串**，实际渲染成：

```
📊 **Bench Dashboard** ([详情]())
跑  大小
```

空链接、缺数字，PR 上天天如此。全仓 `id:` 只有一个（`cache-baseline`），
孤立的 `upload-artifact` 引用一眼可见——**但只有读渲染结果才看得出来**。

**二、`mdbook.yml` 的 `needs` 指向别的 workflow 的 job**

这一处后果严重得多：

```yaml
needs: [bench-core]     # bench-core 是 ci.yml 的 job，不是本 workflow 的
```

`needs` 只能引用同一 workflow 内定义的 job，跨 workflow 没有依赖机制。
GitHub 会把整个 workflow 判为 **Invalid 并拒绝运行**——也就是说 **mdbook
部署从未真正执行过**。而它自己没有任何报错会被提交者看到，只有去 Actions
页面看才发现。

### 第八轮的一处判断失误（记录下来）

修复第一处时，我加了两层保险：`|| echo` 兜底和 `continue-on-error: true`。
实测 `|| echo` 会把退出码转成 0（`bash -c "exit 42 || echo swallowed"` 退出
码仍是 0），而 `continue-on-error` 已经独立承担「不让 job 变红」——两者功能
重叠。已删掉 `|| echo`，保留 `continue-on-error`。

同时移除了用 `hashFiles()` 判断产物存在的那两处。它评估的是 job **开始时**
的文件状态，对同 job 内刚生成的 `${{ runner.temp }}` 文件不作保证。对照
`mdbook.yml` 里另一处 `hashFiles`（检查仓库内已存在的文件）语义完全不同，
不能照搬。改判上传 step 的 `conclusion`。

### 第八轮修复清单

| 缺陷 | 后果 | 处置 |
|------|------|------|
| `steps.upload-artifact.outputs.*` 无来源 | PR 评论空链接、缺值 | 补 `id`，链接改为指向 Actions 页面 |
| `needs: [bench-core]` 跨 workflow | **整个 mdbook workflow 从未运行** | 删除该行；产物本就靠 `download-artifact` 传递 |
| `|| echo` + `continue-on-error` 重复 | 吞掉真实失败原因 | 删 `|| echo` |
| `hashFiles()` 判断同 job 内新文件 | 判断本身不可靠 | 改判上传 step 的 `conclusion` |

### 新增门禁：`audit_workflows.py`

这类缺陷**不可能靠人眼长期盯住**，必须有常驻防线。新脚本覆盖两类：

- 无来源的 `steps.<id>` 引用（step 未声明 `id`）
- 无来源的 `needs` 引用（job 不在本 workflow 内）

接入 `make audit`（`audit-workflows` 目标，同时跑扫描与自检）与 CI 的
`audit-sources` job。该门禁**检查 CI 自己的 YAML**，自指成立。

### 第八轮验证记录

| 验证方式 | 对象 | 结果 |
|----------|------|------|
| 注入原始 `needs: [bench-core]` | 新门禁 | exit 2 ✅ 精确定位到 mdbook.yml |
| 13 个针对性变异 | `_self_check` | 12 个被 exit 2 抓住 |
| 变异 12（`count_needs` 恒 0） | `_self_check` | **未抓住** —— 只影响汇报数字，不影响判据，已写进脚本文档的盲区说明 |
| YAML 解析断言 `needs is None` | mdbook.yml 修复确认 | ✅ 活代码中已无 `needs` |
| `python3 -m ast` | `audit_workflows.py` | 语法 OK ✅ |

**自检本身的两个 bug（靠变异暴露，值得单独记）**：

1. **用例无判别力，且方向搞反了两次**。想验证正则结尾的 `\.` 是否必要，
   先后试过 `steps_context.value`（`steps` 后是 `_`，两种正则都不匹配）和
   让 step 声明 `id: up`（无点版匹配到也不算孤儿）——两次都没构造出差异。
   第三版让该 step **不**声明 `id`，才使变异会误报、用例有判别力。
2. **`except ValueError` 把意外异常冒充成通过**。原写法对「用例本就期望
   报错」和「生产代码意外抛错」都记成字符串 `"ERROR"`，于是变异 10
   （`_normalize_needs` 只处理 list）让单字符串/字典写法抛出 `ValueError`，
   恰好等于期望值，自检误判通过。修正后又暴露一个次序错误：`expected` 在
   判断前已被重建成元组，对 `"ERROR"` 用例恒为假——把判断移到构造之前。

这两条都属于「自检给出假绿灯」，比门禁本身有缺陷更危险。

### 第八轮追加：门禁自己跑不动了（924.7 秒）

运行 `make audit` 时它**没有报错，也没有结束**——连续 31 分钟仍在运行。
`ps` 显示进程处于 `D` 状态（不可中断 I/O 等待），累计 CPU 时间只有 8 秒，
却打开了 `target/debug/.fingerprint/...` 下的文件。

拆开测两个 glob，差异一目了然：

| 表达式 | 耗时 | 命中 |
|--------|------|------|
| `_workspace_crates` 的 `base.glob("**/Cargo.toml")` | **924.7 秒** | 31 |
| `_source_dirs` 的 `d.glob("*/src/**/*.rs")` | **0.0 秒** | 379 |

两者都递归进 `target/` 的 15 万个文件，为什么一个卡死、一个瞬间完成？

```python
mf.parent for mf in base.glob("**/Cargo.toml")
if mf.parent != base and "target" not in mf.parts    # ← 过滤写在结果侧
```

**过滤发生得太晚了**。`glob("**/...")` 必须先走完整棵树，才把命中的路径交给那行
`if` 判断；而 `_source_dirs` 的 glob 从顶层目录出发（`d/*/src/`），`target/` 的
直接子目录里没有 `src/`，那一层就短路了，根本没往深处走。

这正是本轮主题的另一个实例：**门禁不报错，只是不动**。CI 上表现为 job 静默
超时，且没有任何信息指向根因。

改为 `os.walk` + **遍历时**剪枝（`dirnames[:] = [...]` 就地裁剪，这是剪枝生效的
唯一方式）：

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| `_workspace_crates` | 924.7 秒 | **0.02 秒** |
| `make audit` 整体 | >31 分钟未结束 | **20.9 秒** |
| 命中 crate 数 | 30 | **30** |
| 命中集合 | — | **与旧实现逐项相同** |

最后一行是关键：提速必须以判据不变为前提。为此专门做了对照——把新旧两种
遍历方式的结果都 `resolve()` 后求集合差，结果为空。（第一次对照时我把 glob
结果当目录又 `.parent` 了一次，得到 `.../Cargo.toml`，两边数字相同却报 False，
是探针自身写错，已修正后复测。）

剪枝判据 `{"target", "node_modules", ".git"}` 取自 `.gitignore`：构建产物与依赖
树里本就不该有 Cargo.toml。

**新增自检用例 + 3 个变异**：在临时目录的 `target/` 里真放一个 `Cargo.toml`，
剪枝生效时它不该被看见。三个变异全部被 exit 2 抓住——剪枝集合去掉 `target`
（退化为原写法）、`dirnames[:]` 改成非就地赋值（剪枝静默失效，这是最容易
踩的 `os.walk` 陷阱）、剪枝过头（把正常 crate 也剪掉）。第二条断言专门补上
「该留的还在」，防止第一条假绿。

## 第九轮：门禁自身的作用域盲区

第八轮收尾时我留下一条高风险盲区：`audit_workflows.py` 把 step id 收集成
**整个 workflow 的全局集合**。这不是实现疏忽，是我在写自检用例时**主动断言了
错误的行为**——当时那条用例写着「跨 job 的引用同样按全局 id 解析」，期望值是
`[]`。也就是说：自检不但没发现盲区，还把这个盲区钉死成了「正确」。

### 官方文档怎么说

GitHub 的 steps context 定义原文：

> Information about the steps in the current job that have an `id` specified
> and have already run.

"current job" 是明确限定。而 Context availability 表里，`steps` 只出现在
`jobs.<job_id>.steps.*`、`jobs.<job_id>.outputs.<output_id>`、
`jobs.<job_id>.environment.url` 这几处——workflow 级 `env`、`concurrency`、
`run-name` 允许的 context 列表里都没有它。

### 三类修复

| 缺陷 | 后果 | 处置 |
|------|------|------|
| step id 按 workflow 全局收集 | 跨 job 引用被判为合法 | 按 job 分组，逐行判定归属 |
| 无重复 step id 检查 | 引用读到后一个 step 的值，无任何提示 | 新增 `duplicate_step_ids()` |
| jobs 之外的 steps 引用不报 | 该作用域下 context 不可用 | 归属为 `None` 时一律判缺陷 |

实现上必须解决一个前提：**按行判定 job 归属需要位置信息**，而 `yaml.safe_load`
只给出纯数据。所以改用 `yaml.compose()` 取节点对象的 `start_mark/end_mark`。

顺带确认了一个易误伤点：`jobs.<job_id>.outputs.<output_id>` **允许**引用
`steps`（job 自己的 outputs 引用本 job 的 steps 是正常写法）。已补专门用例
钉住，避免作用域收紧后误报。

### 第九个盲区：一个「逃过变异」其实是无害的等价变换

`job_of_line()` 里写 `end` 还是 `end - 1`，两个变异都没被自检抓住。我连试三种
构造想区分它们：

1. 把引用放到 job 最后一行 → 无差异
2. 把 job 值收敛成单行 flow mapping → 无差异
3. 缩小 end 偏移量 → 无差异

原因在 PyYAML 的语义：`end_mark.line` 指向块结束**之后那一行**的行首，job 的
最后一行内容落在 `end - 1` 处。于是 `start <= line <= end` 与
`start <= line <= end - 1` 覆盖**完全相同**的行集合——这是等价变换，不是缺陷。

没有停在「测不出来」这一步，而是去 7 个真实 workflow 上逐行核对：`end - 1`
下「无归属」的 6–40 行**全部**位于 `jobs:` 之前（`name:`、`on:` 等顶层配置），
没有一行是 job 内部内容。确认等价后，删掉了为此写的无用例，并把结论记进脚本
头部的「已知盲区」段落——**这比留一个测不出来的测试更有价值**。

扫描结果与第八轮**逐项一致**，说明收紧作用域没有误伤现有 workflow——这是本次
修改最需要担心的地方（`ci.yml` 有 30 个 job，跨 job 引用极易被误报）。

## 第十轮：`steps` context 的时序盲区

第九轮把 `steps` id 收紧到 job 作用域后，还剩一个盲区：**作用域对了，但顺序没查**。

### 官方语义

GitHub 文档对 `steps` context 的定义里有一个容易被跳过的限定词：

> The `steps` context contains a list of steps **that have an id specified and
> have already run** in the current job.

`have already run` —— 只有**已经跑完**的 step 才会出现在 context 里。于是
「引用了声明上存在、但排在自己后面、还没执行的 step」这一类写法，在第九轮的
判据下完全合法：无来源检查只看 id 是否在本 job 声明过，不看它跑到哪了。

### 真实缺陷：mdbook.yml 的自我引用

扫描发现 `.github/workflows/mdbook.yml` 里有一处：

```yaml
- name: Deploy to GitHub Pages
  id: deployment
  uses: actions/deploy-pages@v4
  environment:
    name: github-pages
    url: ${{ steps.deployment.outputs.page_url }}   # 引用自己
```

这个 step 在**自己的配置里**引用自己的输出。`page_url` 由 `deploy-pages` 在
action 跑完之后才写入，而 `environment.url` 恰好在这个 step 执行**之前**求值，
所以它恒为空字符串。

后果与第八轮那批静默失效同构：不报错、不让 CI 变红，只是部署完成后 environment
页面上永远没有正确的站点链接。

> 一度怀疑 `environment` 整体缩进错了（写在 step 里而非 job 里）。查证后确认
> **step 级 `environment` 是合法的**——GitHub 明确支持在单个 step 上指定
> environment 以获得该环境的 secret 与审批门禁。所以缩进没错，错的只有那个
> `url` 引用本身。修法因此是最小改动：删掉无效的 `url` 行。`environment.name:
> github-pages` 指向 GitHub 为 Pages 预置的 environment，站点 URL 由
> `deploy-pages` 与 Pages 服务登记，无需手写。

### 门禁：新增 `forward_reference_orphans()`

新增 `step_order_by_job()` 用 `yaml.compose()` 取出每个 job 内 step 的
**声明顺序**与行区间，在 `forward_reference_orphans()` 里判定：

- 引用的 id 是**所在 step 自己**的 → 自我引用；
- 引用的 id 声明在**后续 step** 里 → 前向引用；
- 引用的 id 在**前置 step** 里 → 合法。

**只检查 step 内部**是有意的收窄：job 级的 `environment.url` 前向引用部署 step
是**合法**的（environment 的 URL 要等 job 跑完才登记，那时 step 早已执行），
这正是官方 Pages starter workflow 的标准写法。全局扫会把它误伤。

### 踩到的两个坑

**其一：把 `MappingNode` 当序列解包。** `steps` 是 `SequenceNode`，元素直接就是
step 节点本身，不是 key-value 对。写成 `for _k, node in steps.value` 会在**所有**
用例上抛 `cannot unpack non-iterable MappingNode object`——19 个用例同时红，
一眼就能看出是通用 bug 而非某条用例的问题。

**其二：`end_mark` 的边界。** 判定「本行属于哪个 step」时两次猜错：

| 写法 | 结果 |
|------|------|
| `start <= line <= end` | 5 个用例误报 |
| `start < line <= end` | 同样 5 个用例误报 |
| `start <= line < end` | **正确** |

PyYAML 的 `end_mark.line` 是块结束**之后那一行**的行首 0-based 序号，而非最后一行
内容的序号。所以 step 的行区间是**半开区间** `[start, end)`：下界含（`start_mark`
正指向 `- name:` 那一行），上界不含。用 `<= end` 会把**下一个 step 的首行**算进
上一个 step，于是「引用前置 step」被误判成自我引用。

这个坑值得记一笔的是：**两次都只差一个符号，症状完全相同**（都是那 5 个用例误报
成自我引用）。若当时凭直觉再试一个边界，很可能第三次仍是错的组合。真正定位靠的是
打印真实 mark：

```python
node = yaml.compose(text)
# steps 节点 start/end: 6 9；step start/end: 6 9
```

一行 `print` 比三轮猜测更快。

### 验证记录

| 项目 | 结果 |
|------|------|
| 自检（19 用例） | 通过，exit 0 |
| 变异 1：把自我引用原样注入 mdbook.yml | exit 2，`mdbook.yml:126: ... step 'deployment' 自我引用` |
| 变异 2：插入引用后续 deployment step 的前置 step | exit 2，`mdbook.yml:108: ... 引用了尚未执行的后续 step` |
| 误伤验证：job 级 `environment.url` 前向引用 | exit 0，正确放行 |
| 真实 workflow 扫描 | 7 workflow / 6 step 引用 / 58 needs ✅（step 引用由 7 降为 6，因修复了 mdbook.yml 那处） |
| `make audit` | 全绿 |

三次现场均已恢复，`$JCODE_SCRATCH_DIR` 备份已删除。

## 第十一轮：同类 context 排查（否定结论）

第十轮修的是 `steps` context 的时序维度。教训里留了一句「scope 对了不代表时序也
对」，那么同一个问题就该接着问：**还有哪些 context 的限定词是我没查的？**

本轮排查两类：

| 形态 | 含义 | 实测命中 |
|------|------|---------|
| `needs.<job>.outputs.<key>` | 跨 job 传递输出 | **0** |
| `matrix.<key>` | 矩阵维度 | **0** |
| `strategy.<key>` | 矩阵策略 | **0** |

探针是一次性的 `python3 - <<'PY'`，结果不写进仓库。**否定结论同样要留档**，
否则下一轮会原样再查一遍：

```bash
python3 - <<'PY'
import re, glob, collections
pat = re.compile(r"\b(needs|matrix|strategy|github|env|secrets|runner|job|steps)\.[A-Za-z0-9_.-]+")
agg = {}
for p in sorted(glob.glob('.github/workflows/*.yml')):
    for i, line in enumerate(open(p, encoding='utf-8'), 1):
        if line.lstrip().startswith('#'):
            continue
        for tok in pat.findall(line):
            agg.setdefault(tok.split('.')[0], []).append((p, i, tok.strip()))
for root in sorted(agg, key=lambda k: -len(agg[k])):
    print("%-10s %d 次   例: %s" % (root, len(agg[root]), agg[root][0][2]))
PY
```

### 零命中不等于探针坏了

上面这段的关键是它**自带对照组**：`github` 27 次、`env` 10 次、`runner` 3 次
都被正确捕获。若只写 `needs\.|matrix\.` 两个 pattern，拿到全零时无法区分
「仓库里没有」与「正则写错了」——**探针必须有已知非零的阳性对照**，
否则零结果没有信息量。

本轮未改任何门禁代码。这是有意的：没有缺陷就不该有检查，凑出来的规则只会
增加维护成本并在将来误报。

### 附带查出的真实缺口：glob 只认 `.yml`

上面那个探针用的是 `.github/workflows/*.yml`——**这本身就是个缺陷**。
GitHub 同时接受 `.yml` 与 `.yaml`，而门禁的 `WORKFLOW_GLOBS` 只写前者。

后果不是「漏扫历史文件」那么轻：新 workflow 用 `.yaml` 命名时，门禁会
**静默跳过**它并显示全绿，而新文件里的引用缺陷一次也没被查过。这正是本
脚本要防的那类假绿灯，只不过发生在更上一层——不是判据写错，而是**判据
根本没跑**。

核实过程分两步，缺一不可：

```bash
ls -1 .github/workflows/*.yaml 2>/dev/null | wc -l   # → 0
```

| 结论 | 依据 |
|------|------|
| 第十一轮的否定结论**没有**因此失真 | 仓库当前 `.yaml` 数为 0，glob 漏扫未造成实际遗漏 |
| 缺口本身是**真实的** | 注入 `probe.yaml` 后，旧 glob 恰好漏掉它，新 glob 捕获到自我引用 |

第一步容易漏掉。若只看到「结论是对的」就收工，这个缺口会留给下一个人；
必须再问一句「结论对，是因为仓库没问题，还是因为压根没扫？」

### 自检盲区：扩展名对了，目录可能错

给 glob 补自检时，第一次只断言了扩展名覆盖：

```python
for ext in (".yml", ".yaml"):
    if not any(g.endswith(ext) for g in WORKFLOW_GLOBS):
        glob_failures.append("WORKFLOW_GLOBS 不含 `%s`" % ext)
```

变异「把 `.github/workflows/*.yml` 误写成 `.github/*.yml`」时，**自检仍然
绿灯**——扩展名全对，而实际扫描一个文件都找不到。补上目录断言后两个变异
才都被抓住。

这类自检有个共同点值得记住：它检查的是**常量**（`WORKFLOW_GLOBS` 本身），
不是运行结果。而用例表里 19 个用例都直接喂 YAML 文本给 `check_file()`，
走不到「按文件名发现文件」这一步——**glob 退化时它们仍会全绿**。常量断言与
行为断言覆盖的不是同一段代码。

## 五、给下一位接手者的提醒

1. **不要在编译进行中编辑源码**。本轮第一次跑 `make test-all` 得到一个 `unresolved import` 编译错误，看起来像代码缺陷，实际是我在编译 `sisyphus-types` 之后、编译 `sisyphus-mem` 之前改了 `store.rs` 的导入。这类假故障会浪费排查时间。
2. **后台命令要正确传播退出码**。`(cmd > log; echo "EXIT=$?" >> log)` 的退出码是 `echo` 的，永远是 0。本轮据此误判过一次「测试通过」。正确写法：`cmd > log 2>&1; ec=$?; echo "EXIT=$ec" >> log; exit $ec`。
3. **本机并行链接重型测试二进制会 OOM**（19.5 GiB 实测 `-j 2` 也不安全，只有 `-j 1` 稳定）。`make test-*` 已内置该开关，直接敲 `cargo test` 需自行加 `-j 1`。`sisyphus-sandboxd` 另需 `CARGO_PROFILE_DEV_DEBUG=0`（`make test-sandboxd` 已带）。
4. **跨文件复制实现已发生三次**：`peer/fallback.rs`、`cli/resolve_backend`，以及本轮确认的语义漂移（同一通道承担两种职责）。新增逻辑前先找已有实现。
5. **语义相同的两个方法不要共用一个通道**。本轮的教训：`deliver_inbound_experience_sync` 与 `broadcast_experience_sync` 名字不同、注释也写清了差异，实现却完全一样。注释不是约束。
6. **写文档里的行号引用前先想清楚它会不会腐化**。本轮在 workflow 注释里写了 `scan_flaky.py:177`，转头给该脚本加 9 行文档就漂移成 185。改用代码片段（`if not args.keep_going`）而非行号。
7. **工具的默认输出路径未必适合 CI**。`$JCODE_SCRATCH_DIR` 这类本地开发者的环境变量，在 CI 上不会设置，会退回 `/tmp`，进而让 artifact 上传静默失效。接线上线前先确认落盘路径与消费路径指向同一处。
8. **workflow 里写错的引用不会让 CI 变红**。无来源的 `steps.<id>` 引用会静默展开成空字符串（渲染出空链接、缺值）；无来源的 `needs` 引用会让**整个 workflow** 被判 Invalid 而从未运行过——`mdbook.yml` 就这样悄悄死了很久。已加 `scripts/audit_workflows.py` 兜住这两类，但 `hashFiles()` 之类语义问题仍需人判断。
9. **自检里 `except` 分支最容易制造假绿灯**。把「用例本就期望报错」和「生产代码意外抛错」都记成同一个值，变异就能冒充通过（第八轮实测：`ValueError` 恰好等于期望值，自检误判通过）。异常路径必须用不同标记区分，且判断要放在构造期望值**之前**。
10. **构造自检用例时，「看起来相关」不等于有判别力**。第八轮为验证正则里一个字符，连续两次构造的用例都无法区分正确与突变实现。判断标准是：把生产代码改坏后，这个用例会失败吗？构造不出差异就说明用例无效，得换输入而不是改期望。
11. **过滤写在结果侧 = 遍历照样发生**。`glob("**/x") + if "target" not in parts` 是最常见的伪装——代码读起来像剪了枝，实际要先走完 15 万个文件（实测 924.7 秒）。`os.walk` 必须 `dirnames[:] = [...]` **就地**裁剪才能真正剪枝。门禁不报错、只是不动，CI 上表现为无信息的静默超时。
12. **自检用例会把错误的实现钉死成「正确」**。第九轮那条「跨 job 引用按全局 id 解析」用例，把 `steps` context 的作用域盲区写成了期望值——自检绿灯，缺陷却被固化。写用例时要问：这条期望值的依据是**文档**还是**当前实现的行为**？后者意味着在给 bug 拍照。
13. **「测不出来的变异」要先判定是不是等价变换**。`end` 与 `end - 1` 在 PyYAML 上覆盖完全相同的行集合（`end_mark` 指向块结束**之后**那行行首）。连试三种构造无差异后，去真实数据上逐行核对，确认无害才放过——「测不出」不等于「测不了」，也不等于「该加测试」。
14. **scope 对了不代表时序也对**。第九轮把 `steps` id 收紧到 job 作用域，自检全绿，但 `steps` context 还有 `have already run` 这道时间维度——引用未执行的后续 step 同样静默展开为空。修一类盲区时，顺手问一句：同类 context 还有哪些限定词是我没查的。
15. **PyYAML 的 `end_mark.line` 是半开区间的上界**，指向块之后那一行，不是最后一行内容。写范围判定时优先 `[start, end)`，别猜。
16. **症状相同的两个错误未必是同一个**。第十轮 `start <= line <= end` 与 `start < line <= end` 都导致同一批用例误报成自我引用，差别只有一个符号。症状相同的时候要回到数据（`print` 出真实 mark）而不是继续试符号排列。
17. **探针零命中时要先证明探针没坏**。第十一轮查 `needs.<job>.outputs.<key>` 与 `matrix.<key>` 全是 0，若正则本身写错，结论同样是「0」——无法区分。探针必须自带已知非零的阳性对照（那轮用 `github` 27 次 / `env` 10 次），否则零结果没有信息量。
18. **否定结论也要留档**。「查过了，没有问题」和「还没查」在代码里长得一模一样。不写进文档，下一轮会原样再查一遍。
19. **「结论是对的」要问一句「对，是因为没问题还是因为压根没扫」**。第十一轮的 context 排查用 `.yml` glob 得出零命中，结论恰好正确（仓库确实 0 个 `.yaml`），但 glob 本身只认 `.yml` 是个真实缺口——若当时看到结论正确就收工，缺口会留给下一个人。
20. **常量的自检断言与行为断言覆盖不同代码路径**。给 `WORKFLOW_GLOBS` 补的断言只在退化时生效，而 19 个用例都走 `check_file()`，不经过文件发现。写自检前先问：这条用例真的经过了那段代码吗？
