# wasmtime 47 → 48 性能实测（2026-10-10）

## 结论

**wasmtime 48 在稳态 WASM 执行上比 47 慢约 4%–12%（中位数 ~8.5%）。**
升级是**安全修复驱动**的（6 个 RUSTSEC 漏洞），不是为了性能；这个性能代价
是已知且可接受的取舍，不是回归事故。

同时：无退化项也已实测确认——fuel 计账、内存占用、墙钟兜底行为全部一致。

## 测量方法（以及为什么必须这样测）

在共享且有负载的开发机（12 核，load average 3–6.5）上测量，单次结果**完全不可信**：

| 尝试 | 47 | 48 | 结论 |
|------|----|----|------|
| 顺序测，min | 10.9µs | 18.7µs | 48 慢 72% |
| 换探针后顺序测，min | 11.4µs | 9.4µs | **48 反而快** |
| 再测 47，min | 8.8µs | — | 47 比上一轮"快" 20% |

同一版本的 min 在几分钟内能从 8.8µs 漂到 11.4µs，**噪声大于效应量**。
第一轮那个"慢 72%"完全是机器负载的假象。

最终采用：
- **交错执行**：47、48 两个预编译二进制交替运行，看到相同机器状态
- **隔离核心**：`taskset -c 5` 固定到同一核，消除迁移噪声
- **取 min 而非 p50**：中位数随后台负载漂移，最小值逼近无竞争成本
- 每轮 1000 次采样，8 轮交错

复现命令（worktree 停在升级前的 `81e3469`）：

```bash
git worktree add --detach "$WT" 81e3469
# 两边各追加同一探针，cargo test --release --no-run 取出二进制
taskset -c 5 "$WT47_BIN" perf_probe --nocapture | grep PERF2
taskset -c 5 "$BIN48"    perf_probe --nocapture | grep PERF2
```

## 交错实测数据（隔离核心 5）

```
r1 47=8500  48=9600   +12%
r2 47=8500  48=9500   +11%
r3 47=8700  48=9400   +8%
r4 47=8800  48=9200   +4%
r5 47=8400  48=9000   +7%
r6 47=8300  48=9100   +9%
r7 47=8400  48=8800   +4%
r8 47=7900  48=8800   +11%
```

8/8 轮 48 均更慢，中位数 ~8.5%。另一次隔离核心 3 的 4 轮同样 4/4 更慢
（8121→8823、8121→8923、8021→8823、8121→12033）。

冷编译（首次，含 cranelift codegen）另测：47 ≈ 2735µs、48 ≈ 3462µs。
单次采样，噪声大，只能说"未见明显改善"，不足以定量。

## 代价的实际影响

单次执行 ~1µs 级别的差距（8.5µs → 9.2µs）。在 agent 的典型调用模式下，
WASM 执行不是主要耗时——真实成本在 LLM 调用与工具 I/O 上。因此 8.5% 的
相对退化在实际链路里不可测。

若将来 WASM 执行成为热点，正确做法是改**工具级**分配策略（更大的工具用更
高 fuel / 更长墙钟），而不是回退到存在已知 RUSTSEC 漏洞的 47。

## 仍未测量的部分

- 真实生产负载下的分布（`tools/` 下目前只有测试 fixture）
- `sisyphus-core` 认知循环整体基准（`cargo bench -p sisyphus-core`）未做跨版本对照
- 多工具并发场景（pooling allocator 在竞争下的表现）

以上都会影响"是否值得优化"的判断，目前不足以支撑行动。
