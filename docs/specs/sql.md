# SQL AI 开发规范 (SQL AI Spec)

## 1. AI 协同编码标准 (Coding Standards)
- **Schema 驱动生成**：禁止在没有提供完整 DDL (Data Definition Language) 的情况下让 AI 编写复杂查询。
  - *理由*：AI 经常凭空猜测列名和索引，导致生成的 SQL 无法运行或性能极差。
- **性能优先原则**：强制要求 AI 在提供查询的同时，说明该查询将如何使用索引，并分析潜在的全表扫描风险。
- **可读性与维护性**：引导 AI 使用 CTE (Common Table Expressions, `WITH` 语句) 取代深层嵌套的子查询。

## 2. 定向提示策略 (Prompting Patterns)
- **执行计划预判**：*“请分析此查询在千万级数据量下的执行计划，重点说明哪些步骤可能成为瓶颈，并提出索引优化建议。”*
- **防御性查询编写**：*“请在编写此 UPDATE/DELETE 语句时，先提供一个对应的 SELECT 验证语句，以确保影响范围准确无误。”*
- **方言精确化**：*“请严格按照 PostgreSQL 15 的语法编写，利用其特有的 `JSONB` 操作符来优化此查询。”*

## 3. AI 质量验收清单 (Validation Checklist)
- [ ] **索引覆盖**：`WHERE` 和 `JOIN` 条件中的所有关键列是否都有索引支持？
- [ ] **SARGability**：查询条件中是否在列上使用了函数（导致索引失效）？
- [ ] **资源占用**：是否存在可能导致临时表溢出磁盘的超大 `SORT` 或 `GROUP BY` 操作？
- [ ] **事务安全性**：对于多步操作，是否正确使用了事务控制以保证原子性？

## ❌ 常见 AI 误区 (Anti-Patterns)
- **贪婪查询**：使用 `SELECT *` 而非明确列出所需字段。$\rightarrow$ **正确做法**：仅请求必要的列，减少 IO 和网络开销。
- **笛卡尔积风险**：编写缺失 JOIN 条件的查询或使用不当的 CROSS JOIN。$\rightarrow$ **正确做法**：显式定义所有 JOIN 关系并验证结果集大小。
- **在循环中查询**：在应用程序代码中使用循环调用 SQL (N+1 问题)。$\rightarrow$ **正确做法**：使用 `IN` 子句或 `JOIN` 进行批量查询。
