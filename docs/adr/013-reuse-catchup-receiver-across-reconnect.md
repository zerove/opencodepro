# ADR-013：补齐信号跨重连复用接收器，消除静默丢弃

## 背景

ADR-011 引入「Lagged → 广播补齐信号 → 拨号器重发 `SyncRequest`」的补偿链路。
ADR-012 在复核其测试覆盖时发现：`catchup_deferred_while_paging_converges_exactly`
曾经是**假覆盖**——把延后改成丢弃（`drop(catchup_pending)`）用例仍然通过。

装上 tracing subscriber 抓日志后，那次失效的真实原因比「信号落在 `paging = None`」
更靠前一层：**两个分支一次都没执行**，信号根本没进拨号器的接收端。

## 现象

`run_dial_loop` 每次（重）连接都给 `run_stream` 传一份**新**接收器：

```rust
// 修复前
run_stream(..., catchup_rx.as_ref().map(broadcast::Receiver::resubscribe)).await
```

`broadcast::Receiver::resubscribe` 只从订阅那一刻开始计数，**看不到订阅之前
已发出的信号**。于是断连期间（或流任务尚未进入 `select!` 时）发出的补齐信号
被整个跳过。

最关键的细节是它**不报错、无日志**：`tx.send(())` 返回 `Ok`，因为 spawn 阶段
就已经存在一个订阅者（`spawn_static_peers_with_catchup` 内部持有的那份）。
服务端日志里的 `catchup_signalled=true` 只表示 `catchup_tx.is_some()`，
不表示有人听见了。临时探针实测对照：

| 时序 | `send()` | `try_recv()` |
|------|----------|--------------|
| 先发后 `resubscribe`（实际发生的） | `Ok`（无错） | `Empty`（信号丢失） |
| 先 `resubscribe` 后发 | `Ok` | `Ok`（收到） |

即**发送成功 ≠ 信号被消费**。

## 决策

把**同一个**接收器跨重连复用，不再每次重连重新订阅：

- `run_dial_loop` 的参数改为 `mut catchup_rx`，按 `&mut` 传给 `run_stream`。
- `run_stream` 的参数改为 `Option<&mut broadcast::Receiver<()>>`。
- 信号因此留在通道里，重连后第一轮 `select!` 就能取到（容量 1 下多次合并为
  `Lagged`，`recv_catchup` 已把 `Lagged` 视作「需要补齐」）。

顺带记录一处**当时误判为死代码**的日志：`ExperienceSyncHandler` 里 `tx.send()`
失败时打的 `Lagged catchup signal has no subscriber`。本 ADR 早期版本称它在有
peer 任务存活时永不触发，并建议删除；该判断后来被推翻（见「更正」小节）——
未配置静态 peer 的节点上它是活的，因此**保留**。

## 这个窗口会不会丢数据

**不会。** `run_stream` 在每次流建立时无条件发一次全量反熵拉取（ADR-010 引入），
重连即全量补偿。因此即使信号被丢弃，断连期间的丢失也会在重连时补齐，最终仍然收敛。

修复的收益不是「止住数据丢失」，而是：

1. 消除一次**静默的、无日志的**信号丢弃——这类失败一旦出现在别的场景下
   （例如未来去掉建连时的全量拉取）就没有任何可观测性。
2. 让 `catchup_signalled=true` 这个日志重新变得可信。

## 覆盖情况

两个用例，都在 `crates/sisyphus-bridge/tests/cluster_integration.rs`，
覆盖**两个不同**的窗口——这两者此前被混为一谈，必须分开看：

| 用例 | 窗口 | 是否已有过成功流 |
|------|------|------------------|
| `catchup_signal_sent_before_connect_is_still_consumed` | 拨号器已 spawn、首次 Join 尚未完成 | 否 |
| `catchup_signal_sent_while_reconnecting_is_still_consumed` | 已建立的流被断开、到重连完成之间 | 是 |

第二个用例才是「跨重连」的本意：它先让 B 真的连上 A 并跑出一次 `SyncRequest`
（证明确实存在过成功流），再断开这条流，然后才在断流与重连之间发信号。
断言 `join_attempts_seen() >= 2` 正是为了防止它悄悄退化成第一个用例。

两个用例并非冗余：只丢重连窗口信号的判别性变异下，第一个用例通过、第二个用例失败
（见下文「两次变异」）。也就是说，第一个用例对本文档描述的缺陷**完全不敏感**，
第二个用例才是它的守门人。

### 关键：断言计数，不断言数据

这个 bug 在数据上**完全不可见**——`run_stream` 每次建连都无条件全量拉取，
所以信号丢不丢，B 的最终行集合一模一样。只断言收敛状态的用例对它恒真。

因此断言的是**服务端收到的 `SyncRequest` 次数**：

- 首次建连的全量拉取 → 1 次
- 断流后重连的全量拉取 → 共 2 次
- 断流期间发出的信号被消费 → 再触发一次补齐请求 → 共 3 次

计数由 ADR-013 新增的 `sync_requests_seen` 提供（服务端收到请求时自增，早于应答）。
重连是否真的发生过由 `join_attempts_seen` 证明。

### 关键：用 Join 闸门 + 强制断流制造窗口

需要一个「流已断、重连未完成」的确定性时刻。手段有两处：

1. **Join 闸门**（装在**被拨号方**）：`Join` 关闭时挂起，把拨号器卡在
   `connect_and_join`。
2. **强制断流**：服务端主动结束 outbound 流，让拨号方的 `inbound.next()`
   返回 `None`，`run_stream` 走「inbound stream ended」返回 `Err`，回到拨号循环。

闸门**可以反向使用**（关→开）这一点是重连用例的前提：先放行建出流，断流后再
关闸门把重连那次 `Join` 挡住。因此闸门从最初的 `Semaphore` 改成
「`AtomicBool` 标志 + `join_wake` 唤醒广播」——信号量是单调发放的，表达不了「关」。

三个必须踩过才知道的细节：

1. **闸门要装在被拨号方，不是拨号方。** 拨号方 B 连的是 A；把闸门装在 B 自己身上
   毫无作用，B 会直接连上 A 跑完，计数恒为 0（第一版就是这么写的，失败于
   `left: 0`）。
2. **同步点必须选在「拨号方已回到重连路径」，不是「服务端流已结束」。**
   广播 `send` 只保证信号进通道，不保证流已断；即使服务端那一侧已经结束，
   拨号方的 `run_stream` 仍可能在 `select!` 里。最初的版本因此**抖了 4/5**：
   洪泛产生的补齐信号被**旧流**抢先消费掉，计数提前变成 2，落在错误的窗口。
   正确做法是等 `join_attempts_seen()` 增长——`join()` 只在 `run_dial_loop`
   里被调用，而它只能在 `run_stream` 返回之后才再次被调用，所以这个计数增长
   **恰好**意味着「旧流已不复存在，新的流尚未建立」。
3. **`add_permits(n)` 的 `n` 是新增许可数**，传 `usize::MAX >> 1` 会 panic
   （超过 `MAX_PERMITS`）。改成布尔标志后该问题消失。

### 注意：`make test-all` 不包含 bridge

`.cargo/config.toml` 的 `test-all` 显式 `--exclude sisyphus-bridge`（因为 bridge
测试在 CI 会 OOM）。因此本 ADR 涉及的用例必须单独跑：

```bash
cargo test -p sisyphus-bridge --test cluster_integration
```

声称「全量套件通过」时若只跑 `make test-all`，并不覆盖这里任何一行代码。

### 两次变异：一个抓总量，一个判「是否独有」

**变异一（整体还原旧实现）**：把 5 处改回拥有式接收器
（`Receiver::resubscribe`、`run_dial_loop` 拥有式参数、`run_stream` 拥有式参数、
`recv_catchup` 拥有式参数及调用点）。可编译，两个用例都失败（计数 2，应为 3）。

但这只证明「新用例比修复版多测了点东西」，**不能**证明它测的是**重连窗口**——
信号**全部**丢失也会得到同样的失败。

**变异二（判别性变异，只丢重连窗口）**：保留接收器复用，但仅在**已成功连接过
之后**的每轮重连前把接收器彻底排空，首次建连照常消费。这模拟「只有重连丢信号、
首次建连正常」——也就是本文档声称的那个**具体**缺陷。结果：

| 用例 | 变异二结果 |
|------|-----------|
| `catchup_signal_sent_before_connect_is_still_consumed` | **通过** |
| `catchup_signal_sent_while_reconnecting_is_still_consumed` | **失败**（`SyncRequest` 2 次，应为 3 次） |

旧用例通过、新用例失败，连续 3 次结果完全一致。这才是「新用例覆盖的是重连窗口、
且旧用例覆盖不到」的证据：旧用例对该缺陷**完全不敏感**。

这里还有一个值得记下的坑：第一版变异写成
`while rx.try_recv().is_ok() {}`，两个用例**都通过**——变异是空操作。
`try_recv` 在接收器滞后时返回 `Err(Lagged)` 而非 `Ok`，循环立即退出，
而洪泛场景恰恰会把接收器打到滞后。**无效变异比没有变异更危险**：它看起来验证了
一切。若只看「测试通过」就收工，会得出「新用例也没测到重连窗口」的错误结论。
变异必须先自证自己真的改变了行为。

### 四次错误的结论

**第一次：写不出用例。** 本文档最初的小节写的是「没能写出能捕获它的用例，标记为测试
未捕获」。**那是错的。** 当时把「无法构造确定性窗口」当成了外部约束，实际上那只是
**缺少可观测性**——补上 `SyncRequest` 计数与 Join 闸门之后，窗口是确定性的，变异立刻
被捕获。

**第二次：用例名不副实。** 补上可观测性后写出的用例
（`catchup_signal_sent_before_connect_is_still_consumed`）确实捕获了变异，但它的窗口
是「拨号器已 spawn、首次 `Join` 尚未完成」——**从未有过成功流**。而本文档的标题与
决策小节一直写「跨重连」。用「跨重连」描述一个从未建立过连接的窗口是**夸大**，
且混同了两件事：首次连接、连接重试、已建立流后的重连。这属于「用例通过就以为覆盖
到位」的典型形态——它确实通过了变异，但覆盖的是另一个窗口。

因此补上 `catchup_signal_sent_while_reconnecting_is_still_consumed`：先建出真实流、
再断开、然后才在断流与重连之间发信号。它同样通过变异检验，且额外断言
`join_attempts_seen() >= 2` 以防退化。

**第三次：把「有条件」写成了「恒成立」。** 曾断言 `no subscriber` 日志不可达并
建议删除，实测被推翻——未配置静态 peer 的节点上它是活的（见「更正」小节）。

**第四次：「量级很小」。** 曾在代价小节写测试钩子「量级很小」——**凭直觉写的，
从未测过**，恰恰是本文档批评前三轮的那种毛病。实测为每条消息额外 1.1–1.6 µs、
约 3 倍，**不是**可忽略的量级。测的过程中还差点重犯第二次的错：第一版基准
只计生产端 `send` 循环（`unbounded` 通道下 `send` 永不阻塞），测出「-21 ns/条」的
负开销——纯噪声，若就此收手就会得出「钩子免费」，与原来的「量级很小」错得同样
离谱，只是方向相反。

教训有四条：

1. 这个 bug 的数据结果是恒真的，所以在没有计数之前，任何「用例通过」都不构成证据；
   反过来，「写不出用例」也不等于「不可验证」——先问是不是缺观测手段。
2. **通过变异 ≠ 覆盖到位。** 还要核对用例实际落在哪个窗口，是否与结论声称的窗口
   一致。变异只证明「这条代码路径被测到了」，不证明「声称的那个窗口被测到了」。
3. **否定性结论（「不可达」「不会发生」）同样是推理出来的，需要实证。** 而且更容易
   出错——推理的前提往往有隐含条件（这里的前提是「循环体总会执行」）。
4. **量化的措辞（「很小」「可忽略」）也是声明。** 一旦想写「影响很小」，就该去测；
   测出来的结论可能与直觉相反，而测法本身也可能骗人（见第四次：计错对象会得到
   看似合理的噪声数字）。

## 代价

- `run_stream` 的参数从「拥有接收器」变成「借用接收器」，调用方需持有 `mut`。
- `ClusterServiceImpl` 多几个字段（`sync_requests_seen` / `join_attempts_seen`
  两个 `AtomicU64`、`join_admit` 与 `stream_break` 等测试钩子），以及 `Join` 开头
  一次标志位检查。生产路径 `join_admit` 恒为 `true`，检查立即通过，不引入延迟。
  这些字段**无条件编译**（而非 `#[cfg(test)]`）：集成测试位于 `tests/`，链接的是
  未开启 `cfg(test)` 的库，用 `cfg` 门控会让它们在测试里根本不存在。
- 修复本身不增加开销：`broadcast` 通道本来就在，只是省掉了每次重连的一次
  `resubscribe`。
- ~~**但测试钩子确实位于生产路径上**~~ —— **该状态已改变**：outbound 流上的
  `select!` 包装现已按实例隔离（见「遗留」小节），生产路径不再承担它。代价如实记录
  （下列数字为实测，非估计）：
  - `stream()` 的 outbound 流曾被 `async_stream::stream!` 包了一层，每个事件多一次
    `select!` 分派。生产路径 `stream_break` 永不发信号，该分支永不触发，但包装本身
    每条消息都要付。**实测每条消息额外约 1.1–1.6 µs（裸流 ~540–735 ns/条 →
    带钩子流 ~1.6–2.3 µs/条，约 3 倍以上）**。这不是可忽略的量级：一条消息要多花
    的绝对时间比它本身的转换成本还高出一倍以上。现已只在 `gated` 测试构造上启用。
  - `join_attempts_seen` 每个 `Join` 自增一次（每次连接一次，可忽略）。
  - `Join` 入口多一次 `AtomicBool` 检查（每次连接一次，可忽略）。

  这些是为了可验证性付出的固定开销。若将来确定不再需要这些用例，可整体
  移除（届时须同步删除本 ADR 的变异结论）。

  **如何测的**：`crates/sisyphus-bridge/tests/hook_overhead.rs`（默认 `#[ignore]`，
  按需显式运行）对照两种 outbound 流形态——(a) 裸
  `UnboundedReceiverStream`，(b) `async_stream::stream!` 包 `select!`（当前生产
  形态），各 10 万条、5 次取中位数。计时必须覆盖「消费端把 N 条取完」的全过程：
  `unbounded` 通道下 `send` 永不阻塞，只计 `send` 循环等于在测生产者吞吐，
  **测不到消费端每条消息的 `select!` 分派成本**——而那正是钩子的开销所在。
  第一版基准正因为只计生产端，测出「-21 ns/条」这种负开销（纯噪声），
  差点据此断言钩子免费。

  ```bash
  cargo test -p sisyphus-bridge --test hook_overhead -- --ignored --nocapture
  ```

  **这是上界，不是实际占比。** 基准载荷是 `u64` 而非真实 `ProtoEvent`：
  `select!` 的分派成本与元素类型无关，但它**不含** protobuf 序列化、写 socket、
  系统调用的成本。真实路径上这些固定成本会放大分母，使钩子的**相对**开销显著
  下降。所以「约 3 倍」是钩子在最理想（其它开销最小）情形下的比值，
  **不能**直接当成 gRPC 实际吞吐的损失。绝对值也只在同机同负载下有意义。

  **还有一层噪声限制**：裸流自身跨运行会在 540–735 ns/条之间波动（约 35%），
  而「3 倍」这个量级远超该噪声、可信；但任何**几十纳秒量级**的差值都落在噪声
  底之下，不可据此下结论（见「遗留」小节对 `.map(Ok)` 的讨论）。

## 遗留

- 若将来去掉建连时的无条件全量拉取（改为仅靠信号驱动），「首次拉取 vs 信号补齐」
  的计数区分将失效，届时需要新的可观测点。
- ~~**优化候选（尚未实施）**~~ —— **已实施（按实例隔离）。** 断流钩子让每条
  消息多付约 1.1–1.6 µs，而它只服务于测试，因此改为按实例启用：
  `ClusterServiceImpl` 新增 `break_hook_enabled`，生产构造（`new` /
  `with_experience_bank`）置 `false`，`stream()` 直接返回
  `UnboundedReceiverStream::map(Ok)`；只有 `gated` 测试构造置 `true`，才包
  `async_stream::stream!` + `select!`。原计划里的「`join_admit` 式闸门」没有采用——
  实例级布尔更简单，且已用真实重连测试证明断流窗口确定性未受影响。

  配套证据：
  - `tests/hook_overhead.rs` 新增形态 (c) 测量优化后的生产路径。
  - 回归用例 `break_hook_enabled_only_for_gated_construction` 钉住
    「生产关 / 测试开」这条不变量——它**只影响性能不影响功能**，因此若没有这条
    用例，把生产构造改回 `true` 时断流用例仍会全绿、性能却静默回退。已用变异
    （生产构造改 `true`）验证该用例确实失败。
  - 反向变异（`gated` 置 `false`）确认断流测试仍依赖钩子：连续 3 次稳定失败。

  **基准口径更正**：形态 (c) 的 `.map(Ok)` 成本**低于本基准噪声底**，不能称为
  「零成本」。跨多次运行其相对裸流的差值在 −6 ns 到 +109 ns 之间摆动，而裸流
  自身就会波动约 35%。因此既不能声称它免费，也不能量化它要付多少 ns；能站住的
  只有相对量级——被移掉的 `select!` 分派（+1120~+1571 ns/条，3 倍以上）远超噪声。
- ~~`ExperienceSyncHandler` 的 `no subscriber` 日志实际不可达~~ —— **该结论已
  被推翻，见下。** 这条日志**不是死代码**，因此不应按「误导性死代码」删除。

### 更正：`no subscriber` 日志并非死代码

本 ADR 早期版本写「有 peer 任务存活时永远不会触发」，理由是
`spawn_static_peers_with_catchup` 一进来就 `resubscribe` 了一份接收器。
**这条推理漏掉了条件。** `resubscribe` 发生在
`for grpc_addr in &config.peers` 循环**内部**；`peers` 为空时循环体一次都不执行，
没有任何接收器被创建，`catchup_tx.send(())` 因此返回 `Err(SendError)`，
那条日志照常触发。

也就是说，未配置任何静态 peer 的节点（单机启动、纯被拨号、靠服务发现加入的部署）
上，这个分支是**活的**。原有表述把「有 peer 时不可达」误写成了「恒不可达」。

新增用例 `catchup_signal_send_fails_when_peer_list_is_empty` 走真实装配路径
`spawn_static_peers_with_catchup`（而非手工造 `broadcast::channel`——那只能验证
tokio 语义，证明不了生产接线），把该行为钉住。

有效变异：把 `resubscribe` 提到循环之外并 `mem::forget` 强制存活（模拟「peers 为空
时也仍有一个订阅者」），用例稳定失败，连续 3 次一致。

这个更正也再次印证了本 ADR 的一贯教训：**「不可达」这类否定性结论同样需要实证。**
它是推理出来的，不是测出来的；推理的前提（循环体总会执行）恰好在这里不成立。
