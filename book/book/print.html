Sisyphus — 认知计算引擎

Sisyphus 是一个认知计算引擎，用于构建能够通过递归 观察–判断–决策–行动（observe–orient–decide–act，OODA）循环来规划、执行并改进自身行为的自主 AI 代理。

功能概述

Sisyphus 的核心是接收一个高层目标（以自然语言表达），然后：

  1. 合成（Synthesize）标准操作程序（Standard Operating Procedure，SOP）—— 一个由可执行子步骤组成的有向无环图（directed acyclic graph，DAG）。
  2. 执行（Execute）SOP，在可用节点上按依赖关系并行运行。
  3. 模拟（Simulate）通过蒙特卡洛树搜索评估结果，预测成功概率。
  4. 反思（Reflect）执行结果，计算预测与实际结果之间的偏差分数（deviation score）。
  5. 演进（Evolve）SOP，重试失败节点、增加燃料预算，或重构图结构。

该循环持续进行，直到目标收敛（偏差低于阈值）或达到最大迭代次数。

为什么选择 Sisyphus？

  • 自我改进：引擎从每次执行中学习，无需人工干预即可演进其 SOP。
  • 设计即安全：工具代码在 WASM 沙箱中执行，带燃料上限与内存边界。
  • 可观测：每个认知操作都内置 Prometheus 指标。
  • 可组合：每个 crate 相互独立，可按需取用。

关键设计决策

  • trait 方法不使用 async：需要异步执行的 trait 方法使用 async_trait。
  • WASM 优先的工具：所有外部工具代码在带燃料与内存限制的沙箱 WASM 实例中运行。
  • 处处埋点：每个重要操作都记录 Prometheus 指标以便观测。
  • 两级缓存：L1（内存 DashMap）+ L2（sqlx + SQLite）提供快速键值存储。

沙箱：嵌入式与守护进程架构

WASM 沙箱有两种运行模式，由 Config.sandbox.use_sandboxd 控制：

嵌入式模式（use_sandboxd = false，默认）

┌───────────────┐     ExecuteTool     ┌─────────────────┐
│   gRPC Bridge  │ ──────────────────> │  WasmToolExecutor │
│               │ <────────────────── │  (wasmtime)      │
└───────────────┘     return result   └─────────────────┘
  • wasmtime 在 bridge 进程中内嵌运行。
  • 部署简单，无 IPC 开销。
  • OOM 风险：cranelift JIT 内存在进程退出前不会释放。
  • 适合开发与低吞吐场景。

守护进程模式（use_sandboxd = true）

┌───────────────┐     gRPC (IPC)     ┌──────────────────┐
│   gRPC Bridge  │ ──────────────────> │ sisyphus-sandboxd │
│               │ <────────────────── │  (wasmtime)       │
└───────────────┘     return result   └──────────────────┘
         │                                │
         │ 启动时生成子进程                │ 每次调用独立的 WASM
         │ 退出时回收                    │ 实例生命周期
         ▼                                ▼
   子进程池                       燃料门控执行

Bridge 启动时生成 sisyphus-sandboxd 作为受管子进程，优雅关闭时回收。通信通过本地 gRPC（tonic）通道进行，守护进程监听 127.0.0.1:0（临时端口）。

优势：

  • 进程级隔离：sandboxd 崩溃不会拖垮 bridge。
  • 内存隔离：每次 WASM 调用可在全新的守护进程进程中运行。
  • 独立扩展：守护进程可部署在单独的硬件上。
  • OOM 缓解：守护进程可在不中断 bridge 的情况下重启。

配置：

  • sandboxd_path：sisyphus-sandboxd 二进制路径，默认为 PATH 搜索。
  • 守护进程通过自己的 gRPC 服务接收 wasmtime 执行请求，使用与 ExecuteTool 类似的契约。

DAG 执行

Sisyphus 使用基于入度跟踪的并行拓扑执行器执行 SOP 图。

算法

代码：核心执行器

#![allow(unused)]
fn main() {
// 简化为 sisyphus-core::Executor
pub async fn execute_with_context(
    &self, sop_graph: &SOPGraph, start_node: NodeIndex, initial_ctx: Option<Arc<ExecutionContext>>,
) -> Result<Arc<ExecutionContext>, String> {
    // 校验无环
    toposort(&sop_graph.graph, None).map_err(|_| "SOPGraph contains cycles")?;

    let ctx = initial_ctx.unwrap_or_else(|| Arc::new(ExecutionContext::new()));
    let mut join_set = JoinSet::new();
    let mut in_degree: HashMap<NodeIndex, usize> = HashMap::new();

    // 初始化入度计数
    for node in sop_graph.graph.node_indices() {
        let degree = sop_graph.graph.edges_directed(node, Incoming).count();
        in_degree.insert(node, degree);
        if degree == 0 {
            let ctx = ctx.clone();
            let node = sop_graph.graph[node].clone();
            join_set.spawn(async move { node.execute(&ctx).await });
        }
    }

    // 随完成处理结果
    while let Some(result) = join_set.join_next().await {
        let (node_id, output) = result.map_err(|e| format!("Join error: {}", e))??;
        // 在上下文中存储输出
        ctx.set(&sop_graph.graph[node_id].name(), output).await;
        // 扇出到下游节点
        for edge in sop_graph.graph.edges_directed(node_id, Outgoing) {
            let target = edge.target();
            let degree = in_degree.get_mut(&target).unwrap();
            *degree -= 1;
            if *degree == 0 {
                // 启动现在就绪的节点
            }
        }
    }

    Ok(ctx)
}
}

错误处理

  • 环检测：toposort() 在执行前拒绝环形图
  • 节点错误：向上传播，认知循环捕获并演进 SOP
  • Join 错误：Tokio 任务 panic 被捕获并作为错误返回

燃料与内存

每个节点使用其配置的燃料预算执行。Wasmtime 的燃料计量跟踪 WASM 指令消耗。耗尽时触发 ResourceExhausted，认知循环据此为重试调整燃料。

关键实现：execute_with_cognition()

#![allow(unused)]
fn main() {
// 简化为 sisyphus-core
async fn execute_with_cognition(
    &self, graph: &SOPGraph, start: NodeIndex, sop_id: &str, ...
) -> Result<(NodeOutput, String, Option<SOPGraph>), String> {
    let mut current_ref = graph.clone();
    let max_iter = 10;

    for iteration in 0..max_iter {
        // 1. 预测结果
        let prediction = intel.simulator.simulate(&current_ref, &ctx, sop_id).await?;

        // 2. 执行 SOP
        let final_ctx = executor.execute_with_context(&current_ref, start, None).await?;

        // 3. 构建轨迹并反思
        let trace = build_trace(&current_ref, &final_ctx);
        let reflection = intel.reflector.reflect(&trace, &prediction).await?;

        // 4. 检查收敛
        if reflection.deviation_score < CONVERGENCE_THRESHOLD {
            return Ok((result, report, None));  // 完成
        }

        // 5. 演进并重试
        let evolved = intel.evolver.evolve(&current_ref, &reflection, &prediction)?;
        current_ref = evolved;
    }

    Err("Max iterations exceeded".into())
}
}

收敛条件

循环在满足以下任一条件时终止：

  • 偏差阈值：deviation_score < 0.15（预测与实际匹配）
  • 最大迭代：循环 10 次未收敛
  • 无演进：Evolver 返回结构相同的 Ok(graph)（无可改进）

SOP 编排

SOP 是一个有向无环图（directed acyclic graph，DAG），表示达成特定目标的过程。

结构

graph LR
    G[Goal] --> N1[Node 1<br/>fetch data]
    G --> N2[Node 2<br/>process]
    G --> N3[Node 3<br/>validate]
    N1 --> N4[Node 4<br/>merge]
    N2 --> N4
    N3 --> N4
    N4 --> R(Result)

每个节点包含：

  • 名称（Name）：SOP 内的唯一标识符
  • 描述（Description）：步骤的语义描述（用于合成与反思）
  • 工具类型（Tool Type）：要调用的 WASM 工具二进制
  • 燃料预算（Fuel Budget）：该节点的 WASM 指令上限（默认 10,000）
  • 最大重试次数（Max Retries）：失败时重试次数
  • 超时（Timeout）：最大墙钟时间（默认 30s）

生命周期

stateDiagram-v2
    [*] --> Synthesized: GoalDrivenSynthesizer
    Synthesized --> Executing: DagExecutor
    Executing --> Succeeded: All nodes OK
    Executing --> Failed: Node error
    Failed --> Evolved: StandardEvolver
    Evolved --> Executing: Retry with modifications
    Succeeded --> [*]
    Failed --> [*]: Max iterations exceeded
  1. 合成（Synthesize）：GoalDrivenSynthesizer 从自然语言目标生成 SOP 图
  2. 执行（Execute）：Executor 按拓扑序运行 DAG，独立节点并行执行
  3. 演进（Evolve）：反思后 SOP 可能被变异，新增节点、调整燃料预算或重构图子图

演进操作

操作说明
重试包装为失败节点包装重试逻辑（增加燃料）
燃料增加为耗尽燃料的节点提升燃料预算（每次重试 2×）
子图重构重排或拆分节点以获得更好的并行性（未来）

执行流程

  1. 合成：FlowSynthesizer::synthesize() 将自然语言目标转换为 SOPGraph
  2. 执行：Executor::execute_with_context() 按拓扑序运行 DAG，独立节点通过 tokio::task::JoinSet 并行执行

sisyphus-intel — 认知与模拟

Sisyphus 的“大脑“ — 四项核心认知能力：流程合成（flow synthesis）、模拟（simulation）、反思（reflection）与演进（evolution）。

四个认知 traits

1. FlowSynthesizer（合成）

将自然语言目标转换为类型化动作的 DAG：

#![allow(unused)]
fn main() {
#[async_trait]
pub trait FlowSynthesizer: Send + Sync {
    async fn synthesize(&self, goal: &str, context: &ExecutionContext)
        -> Result<SynthesisResult, String>;
}
}

实现：GoalDrivenSynthesizer — 基于关键词的解析器，将动作动词（fetch、process、store、search、validate）映射为线性或并行 DAG 流水线。

2. Simulator（预测）

运行前估算成功概率与执行成本：

#![allow(unused)]
fn main() {
#[async_trait]
pub trait Simulator: Send + Sync {
    async fn simulate(&self, graph: &SOPGraph, ctx: &ExecutionContext, sop_id: &str)
        -> Result<SimulationResult, String>;
}
}

实现：MonteCarloSimulator — 对 DAG 进行随机路径采样。计算混合路径概率与估算成本。使用状态存储中的执行历史，使采样偏向历史上成功的路径。

3. Reflector（分析）

对比预测与实际结果：

#![allow(unused)]
fn main() {
#[async_trait]
pub trait Reflector: Send + Sync {
    async fn reflect(&self, trace: &str, prediction: &SimulationResult)
        -> Result<ReflectionReport, String>;
}
}

实现：StandardReflector — 基于字符串的错误分类，构建偏差分数（0.0 = 完全匹配），生成结构化改进建议。

4. SOPEvolver（自适应）

反思后变异 SOP：

#![allow(unused)]
fn main() {
#[async_trait]
pub trait SOPEvolver: Send + Sync {
    fn evolve(&self, graph: &SOPGraph, report: &ReflectionReport, prediction: &SimulationResult)
        -> Result<SOPGraph, String>;
}
}

实现：StandardEvolver — 用重试逻辑包装失败节点，调整燃料预算。使用 SimpleFuelPricer（线性）或 AdaptiveFuelPricer（指数退避）。

错误分类

架构

┌──────────┐   write-back     ┌──────────┐   optional   ┌────────────┐
│   L1     │ ◄─────────────── │   L2     │ ◄─────────── │  pgvector  │
│  LRU     │    (buffered)    │  SQLite  │   (ANN index) │ (Postgres) │

构造

fn main() {

// 自定义路径与内存限制

}

创建带以下配置的 Wasmtime Engine：

  • 池化实例分配：预分配内存池，快速实例化
  • 内存限制：每实例最大内存可配置（默认 10 页 = 640 KiB）
  • 燃料计量：可配置燃料上限，防止失控执行（默认 10,000）
  • 栈限制：最大 1,000,000 个 WASM 栈帧

执行流程

  1. 加载：从 {tools_path}/{tool_id}.wasm 读取 .wasm 二进制
  2. 编译：编译为 Wasmtime Module（缓存在 DashMap 中避免重新编译）
  3. 实例化：创建带每次调用燃料分配的实例
  4. 调用：调用导出的 run 函数，传入输入字节
  5. 返回：返回输出字节，或燃料/内存耗尽错误

        // ...
    }
}

错误处理

错误含义认知循环响应
ResourceExhausted: fuelWASM 指令耗尽以 2× 燃料重试
ResourceExhausted: memory超过线性内存限制失败 — 重新设计节点
Unknown export: runWASM 模块没有 run 导出失败 — 无效工具
I/O 错误工具文件未找到失败 — 缺少工具

燃料系统

Wasmtime 的燃料计量跟踪 WASM 指令消耗。燃料耗尽时立即中止执行。认知循环将其解释为通过 AdaptiveFuelPricer 以增加燃料重试的信号。

控制台输出捕获

WASM 模块的 stdout/stderr 通过 WasmtimeConsole 捕获并经 tracing 路由。

#![allow(unused)]
fn main() {
let registry = build_provider_registry(&configs)?;
if let Some(shared) = registry.shared_http() {
    // 等待 in-flight 请求完成（最多 5 秒）
    let _ = shared.shutdown(Duration::from_secs(5)).await;

}

关闭后新请求会被快速失败（on_request_start 返回 false），不再向已关闭系统发起新请求。

性能

Sisyphus 包含多项性能优化。

流水线批处理

节点根据历史执行时间进行自适应批次执行：

  • 快速节点（<50ms）：较大批次（1.5x）
  • 慢速节点（>500ms）：较小批次（0.7x）
  • 中等节点：保持当前批次大小

输出去重缓存

OutputCache 存储内容哈希索引的结果，避免重复执行相同计算：

  • 1000 条目容量
  • 基于内容哈希（确定性）
  • 达到容量自动逐出

上下文压缩

大上下文值自动压缩：

  • 字符串超过阈值：截断并加标记
  • 对象超过 10 个键：仅保留前 10 个键

执行性能分析器

跟踪每个节点的执行指标：

  • 按节点类型的平均时长
  • 缓存命中率
  • 最慢节点列表

性能调优

缓存调优

OutputCache 的逐出策略与容量可针对不同工作负载调优。

参数默认值说明建议
缓存容量1000逐出前的最大条目数重复工作负载时增大
上下文阈值4096触发压缩前的字节数内存受限时减小
批次基数4初始流水线批次大小高吞吐时增大

权衡：更大的缓存以减少重复执行为代价占用更多内存。通过性能分析器监控缓存命中率。命中率低于 60% 时考虑增大容量。超过 95% 时减小容量可释放内存且不影响性能。

Sandboxd 模式选择

沙箱守护进程（sandboxd）可运行在两种模式：

模式延迟隔离使用场景
嵌入式~50µs进程开发、可信工作负载
守护进程~500µs容器生产、不可信代码
  • 嵌入式在进程内实例化 Wasm 运行时。延迟最低，但无容器级隔离。适合开发与 CI。
  • 守护进程通过 gRPC 与单独的 sandboxd 进程通信。每次调用延迟更高，但提供容器级沙箱。

在 Config.tool_executor 中通过配置工具执行器切换模式。守护进程模式是生产部署的默认。

并发任务调优

# config.toml
[cognitive_loop]
max_iterations = 30           # 认知迭代次数上限
convergence_threshold = 0.15  # 偏差低于此值时停止

注：ParallelBranchPredictor 已移除（从未接入生产循环，见 ADR 005 修订）。 DAG 节点级并发由 [executor] max_concurrent_tasks 控制。

调优指南：

  • max_concurrent_tasks：CPU 密集型工作负载设置为 CPU 核心数。I/O 密集（LLM 调用）时，更高值（8-16）可提升吞吐量。
  • max_iterations：更低的值降低最坏情况延迟。更高的值提升收敛质量。
  • convergence_threshold：更严格（更低）的阈值提升输出质量，但需要更多迭代。

使用 RUST_LOG=sisyphus_core=info 通过 tracing spans（predict、execute、reflect、evolve）监控认知循环性能。

评测器在 evals/runner.rs 中实现，自动加载 evals/<agent>/cases.json 下的全部用例，按代理分组执行，并汇总得分。

用例结构

每个代理目录下的 cases.json 是一组用例（Case）。字段如下：

字段类型说明
idstring用例唯一标识
agentstring目标代理：metis、momus、librarian、scribe、SecurityOracle
inputobject传入工具的参数（随代理而异）
expectedobject基准输出或关键组成
criteria[]array判据列表
metadataobject（可选）类别与难度（easy/medium/hard）

用例结构由 evals/schema.json（JSON Schema draft-07）定义。eval-runner 启动时会用该 schema 校验全部用例文件，不合规则立即报错退出，防止无效用例混入。

判据类型

每个 criteria 条目通过 check_type 选择验证方式：

类型说明示例 expected_value
keyword输出文本包含指定关键字## Context
regex输出文本匹配正则\[Core Conclusions\].*\[Detailed Evidence\]
json_schema输出 JSON 匹配子 schema{"type": "object", ...}
llm_judgeLLM 判官评估输出是否符合语义标准The decision must explicitly state ...

weight（默认 1.0）控制判据在用例总分中的占比。用例得分为通过的判据加权和除总权重，全部通过才算 PASS。

评测模式

EvalRunner 依据环境变量选择 LLM 客户端：

  • LLM_API_KEY=mock（默认）：使用内置 MockLlmClient，所有代理工具直接返回固定结构。此模式用于验证管线与结构，无真实智能，llm_judge 判据会按结构匹配。
  • 设置真实 LLM_API_KEY/LLM_ENDPOINT/LLM_MODEL：使用 DynamicLlmClient 调用真实模型，全量判据（含 llm_judge）按语义评估，得到真实能力得分。

添加用例

  1. 确定目标代理与覆盖缺口，选择 evals/<agent>/cases.json 追加用例；
  2. 明确 check_type：结构固定用 keyword/regex，语义判断用 llm_judge，大对象校验用 json_schema；
  3. 运行 make eval-check 确认通过编译；
  4. 运行 make eval 确认新用例被加载并校验。

安全

API 密钥认证

所有 API 端点需要通过以下方式认证：

  1. 请求头（Header）：X-API-Key: <your-key>
  2. Bearer：Authorization: Bearer <your-key>

密钥与配置中的 api.key 字段比对。

外部目录权限

external_dir_permissions 配置控制引擎可访问的目录：

[tools]
external_dir_permissions = [
    { dir = "/project", write = true },
    { dir = "/tmp", write = true },
    { dir = "/home", write = false }
]

环境变量替换

配置值支持环境变量替换：

  • {env:VAR_NAME} - 使用环境变量，缺失时报错
  • {env:VAR_NAME|default} - 使用环境变量，带默认值回退
  • {env:VAR_NAME:} - 使用环境变量，缺失时为空字符串

RBAC（基于角色的访问控制）

角色：admin、user、viewer、guest

角色权限
admin完全访问
user执行、读取、写入
viewer只读
guest仅健康检查

会话隔离

会话按会话 ID 隔离。每个会话维护：

  • 独立的消息历史
  • 独立的记忆上下文
  • 独立的 DAG 执行状态

沙箱执行

WASM 沙箱为工具执行提供进程隔离：

  • 通过 wasmtime 配置限制内存
  • 基于燃料的指令限制
  • 不允许访问允许目录之外的文件系统
  • 无网络访问（除非明确授予）
