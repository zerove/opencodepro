Sisyphus Documentation

Sisyphus — Cognitive Computation Engine

Sisyphus is a cognitive computation engine for building autonomous AI agents that plan, execute, and improve their behavior through a recursive observe–orient–decide–act (OODA) loop.

What It Does

At its core, Sisyphus takes a high-level goal (expressed in natural language) and:

  1. Synthesizes a Standard Operating Procedure (SOP) — a directed acyclic graph (DAG) of executable sub-steps.
  2. Executes the SOP in parallel across available nodes, respecting dependencies.
  3. Simulates outcomes via Monte Carlo tree search to predict success probability.
  4. Reflects on execution results — computing a deviation score between predicted and actual outcomes.
  5. Evolves the SOP — retrying failed nodes, increasing fuel budgets, or restructuring the graph.

This loop continues until the goal converges (deviation below threshold) or a maximum iteration limit is reached.

Why Sisyphus?

  • Self-improving: The engine learns from every execution, evolving its SOPs without human intervention.
  • Safe by design: WASM sandboxing for tool code execution with fuel limits and memory bounds.
  • Observable: Built-in Prometheus metrics for every cognitive operation.
  • Composable: Each crate is independent; use just the parts you need.

Project Status

Sisyphus is in active development (v0.1.0). The core cognitive loop is functional and tested, with WASM tool execution, multi-level caching, and Prometheus metrics integration.

Key Design Decisions

  • No async in trait methods: The system uses async_trait for trait methods that need async execution.
  • WASM-first tooling: All external tool code runs in sandboxed WASM instances with fuel and memory limits.
  • Metrics everywhere: Every significant operation records Prometheus metrics for observability.
  • Two-level cache: L1 (in-memory DashMap) + L2 (SQLite via sqlx) for fast key-value storage.

Configuration

Sisyphus is configured via TOML files deserialized into the sisyphus_types::Config struct.

An example configuration file is provided at config.example.toml in the project root.

Default Configuration

[cognitive_loop]
max_iterations = 10
convergence_threshold = 0.15

[executor]
max_concurrent_tasks = 16
default_fuel = 1_000_000

[cache]
l1_capacity = 10_000
database_url = "sqlite:data/sisyphus.db"
enable_vectors = false
vector_dimension = 1536

[metrics]
prometheus_port = 9100

[sandbox]
max_memory_pages = 10
default_fuel = 1_000_000
wasm_tools_dir = "tools"

Database Backends

The database_url in [cache] supports two backends:

URL PrefixBackendVector Support
sqlite:SQLite (default)Full scan + memory cosine similarity
postgres://PostgreSQLpgvector ANN (<-> operator)

PostgreSQL / pgvector

For semantic similarity search with ANN indexes:

  1. Install the vector extension on your Postgres server
  2. Set database_url = "postgres://user:pass@host/sisyphus"
  3. Set enable_vectors = true and vector_dimension = 1536 (or your embedding model’s dimension)
  4. SqlStore automatically runs CREATE EXTENSION IF NOT EXISTS vector on connect

Override Order

  1. Default values (hardcoded in each sub-config’s Default impl)
  2. Config file (path set via SISYPHUS_CONFIG env var or Config::from_file())
  3. Environment variables (prefixed with SISYPHUS_, highest priority)

SDK Reference

Sisyphus provides official SDKs for TypeScript, Python, and Go.

TypeScript SDK

npm install @sisyphus/sdk

import { SisyphusClient } from '@sisyphus/sdk';

const client = new SisyphusClient({ baseUrl: 'http://localhost:8080' });

// Health check
const health = await client.health();
console.log(health.status); // "ok"

// Sessions
const sessions = await client.listSessions();
const session = await client.createSession('my-session');

// Search
const results = await client.searchMemory('my query', 10);

// Execute SOP
const result = await client.executeSop('sop-id');
console.log(result.status); // "success"

Python SDK

pip install sisyphus-sdk

Go SDK

go get github.com/sisyphus/sdk-go

package main

import (
    "fmt"
    sisyphus "github.com/sisyphus/sdk-go"
)

func main() {
    client := sisyphus.NewClient("http://localhost:8080", "")

    // Health check
    health, _ := client.Health()
    fmt.Println(health.Status) // "ok"

    // Sessions
    sessions, _ := client.ListSessions()
    session, _ := client.CreateSession("my-session")

    // Search
    results, _ := client.SearchMemory("my query", 10)

    // Execute SOP
    result, _ := client.ExecuteSOP("sop-id", nil)
    fmt.Println(result.Status) // "success"
}

Performance

Sisyphus includes several performance optimizations.

Pipeline Batching

Nodes are executed in adaptive batches based on historical execution times.

  • Fast nodes (<50ms): Larger batches (1.5x)
  • Slow nodes (>500ms): Smaller batches (0.7x)
  • Medium nodes: Maintain current batch size

Output Deduplication Cache

The OutputCache stores content-hash indexed results to avoid re-executing identical computations.

  • 1000 entry capacity
  • Content-hash based (deterministic)
  • Automatic eviction on capacity

Context Compression

Large context values are automatically compressed:

  • Strings > threshold: Truncated with marker
  • Objects > 10 keys: Kept first 10 keys

Execution Profiler

Tracks per-node execution metrics:

  • Average duration by node type
  • Cache hit rate
  • Slowest nodes list

Benchmarks

cargo bench -p sisyphus-core

Benchmark results are stored in target/criterion/.

Security

API Key Authentication

All API endpoints require authentication via:

  1. Header: X-API-Key: <your-key>
  2. Bearer: Authorization: Bearer <your-key>

The key is validated against the api.key field in configuration.

External Directory Permissions

The external_dir_permissions config controls which directories the engine can access:

[tools]
external_dir_permissions = [
    { dir = "/project", write = true },
    { dir = "/tmp", write = true },
    { dir = "/home", write = false }
]

Environment Variable Substitution

Config values support env var substitution:

  • {env:VAR_NAME} - Use env var, error if missing
  • {env:VAR_NAME|default} - Use env var with fallback
  • {env:VAR_NAME:} - Use env var, empty string if missing

RBAC (Role-Based Access Control)

Roles: admin, user, viewer, guest

RolePermissions
adminFull access
userExecute, read, write
viewerRead-only
guestHealth check only

Session Isolation

Sessions are isolated by session ID. Each session maintains:

  • Separate message history
  • Separate memory context
  • Separate DAG execution state

Sandbox Execution

The WASM sandbox provides process isolation for tool execution:

  • Memory limits via wasmtime config
  • Fuel-based instruction limits
  • No filesystem access outside allowed directories
  • No network access (unless explicitly granted)
