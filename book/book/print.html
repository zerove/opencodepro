Sisyphus Documentation

Sisyphus — 认知计算引擎

Sisyphus 是一个认知计算引擎，用于构建能够通过递归 观察–判断–决策–行动（observe–orient–decide–act，OODA）循环来规划、执行并改进自身行为的自主 AI 代理。

功能概述

Sisyphus 的核心是接收一个高层目标（以自然语言表达），然后：

  1. 合成（Synthesize）标准操作程序（Standard Operating Procedure，SOP）—— 一个由可执行子步骤组成的有向无环图（directed acyclic graph，DAG）。
  2. 执行（Execute）SOP，在可用节点上按依赖关系并行运行。
  3. 模拟（Simulate）通过蒙特卡洛树搜索评估结果，预测成功概率。
  4. 反思（Reflect）执行结果，计算预测与实际结果之间的偏差分数（deviation score）。
  5. 演进（Evolve）SOP，重试失败节点、增加燃料预算，或重构图结构。

该循环持续进行，直到目标收敛（偏差低于阈值）或达到最大迭代次数。

为什么选择 Sisyphus？

  • 自我改进：引擎从每次执行中学习，无需人工干预即可演进其 SOP。
  • 设计即安全：工具代码在 WASM 沙箱中执行，带燃料上限与内存边界。
  • 可观测：每个认知操作都内置 Prometheus 指标。
  • 可组合：每个 crate 相互独立，可按需取用。

项目状态

Sisyphus 处于积极开发中（v0.1.0）。核心认知循环已可用并通过测试，具备 WASM 工具执行、多级缓存与 Prometheus 指标集成。

快速开始

本指南将带你完成 Sisyphus 的安装设置、认知引擎的运行，以及第一个 SOP 的执行。

环境要求

开始之前，请确保系统满足以下要求：

组件要求说明
Rustnightly (1.98.0+)wasmtime/cranelift 要求；stable 在 bridge 上有 ICE (1.96.0)。已提供 rust-toolchain.toml 覆盖。
Go1.21+构建 Go SDK（crates/sisyphus-sdk-go）所需。
Node.js20+TypeScript SDK 与 MCP 工具服务器（workers/ts-tools-mcp）所需。
操作系统Linux / macOSWindows 暂不支持 bridge 与 sandbox。

安装 Rust nightly：

rustup toolchain install nightly
rustup default nightly

验证环境：

rustc --version  # 应显示 nightly-2026-xx-xx 或类似版本
cargo --version

快速开始

1. 克隆并构建

git clone https://github.com/zeronhq/sisyphus-wasm.git
cd sisyphus-wasm

# 检查工作区（为提速排除重型 bridge/sandbox crate）
make check-all

# 构建完整工作区
make build-all

注意： 完整 cargo check --workspace 在内存低于 16 GB 的机器上可能 OOM，因为 sisyphus-sandbox 和 sisyphus-bridge 引入了 wasmtime/cranelift。日常开发请使用 make check-all（排除重型 crate）。

2. 配置

复制示例配置并按需调整：

cp config.example.toml config.toml

默认配置可直接使用位于 http://localhost:8000/v1/chat/completions 的 LLM 端点。设置 SISYPHUS_LLM_API_KEY 和 SISYPHUS_LLM_ENDPOINT 指向您的 LLM 提供商：

export SISYPHUS_LLM_API_KEY="your-api-key"
export SISYPHUS_LLM_ENDPOINT="https://api.openai.com/v1/chat/completions"
export SISYPHUS_LLM_MODEL="gpt-4o"

查看配置页面了解所有可用选项。

3. 运行 Bridge

gRPC bridge 是引擎的主要入口，同时暴露 gRPC（端口 50051）与 HTTP REST（端口 8080）API：

cargo run -p sisyphus-bridge

默认情况下 bridge 监听 http://[::1]:50051（IPv6，自动回退 IPv4）。可用以下方式覆盖：

cargo run -p sisyphus-bridge -- --address http://127.0.0.1:50051

您会看到 bridge 已启动的日志输出：

[2026-07-30T11:40:00Z INFO  sisyphus_bridge] Starting gRPC bridge on [::1]:50051
[2026-07-30T11:40:00Z INFO  sisyphus_bridge] HTTP REST API on [::1]:8080

4. 连接 TUI

在另一个终端中启动终端用户界面（Terminal User Interface，TUI）：

cargo run -p sisyphus-cli

如果 bridge 运行在非默认地址，通过 --bridge 标志指定：

cargo run -p sisyphus-cli -- --bridge http://127.0.0.1:50051

TUI 连接 bridge 并显示主控制台。按 Ctrl+N 创建新会话，然后用自然语言输入一个目标。

参见 TUI 指南 了解键盘快捷键与功能。

5. 用健康检查验证

bridge 运行后，用快速 REST API 调用验证连通性：

curl http://[::1]:8080/health

预期响应：

{"status":"ok","version":"0.1.0"}

简单示例：执行一个 SOP

bridge 运行且 TUI 已连接后，按以下步骤操作：

  1. 新建会话 — 在 TUI 中按 Ctrl+N。
  2. 输入目标 — 输入自然语言目标，例如： 
    Create a Markdown file named "hello-sisyphus.md" with the content "# Hello, Sisyphus!"
  3. 观察认知循环 — 引擎将：
    • 合成 SOP（子步骤 DAG）
    • 使用 WASM 工具或 LLM 调用执行每个步骤
    • 反思结果，必要时演进 SOP
    • 目标达成时收敛
  4. 查看结果 — 完成的会话显示执行的步骤、偏差分数与最终输出。

您也可以通过 REST API 交互：

# 提交目标
curl -X POST http://[::1]:8080/v1/goals \
  -H "Content-Type: application/json" \
  -d '{"goal": "Create a Markdown file named hello-sisyphus.md with content: # Hello, Sisyphus!"}'

# 查询目标状态（将 {id} 替换为返回的目标 ID）
curl http://[::1]:8080/v1/goals/{id}

# 列出所有目标
curl http://[::1]:8080/v1/goals

以库方式运行 SOP（Rust）

如果您将 Sisyphus 作为库集成：

use sisyphus_core::kernel::SisyphusKernel;
use sisyphus_types::config::Config;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = Config::from_file("config.toml")?;
    let mut kernel = SisyphusKernel::new(config).await?;

    let result = kernel.execute_goal("Create a file named hello.md").await?;
    println!("Result: {:?}", result);

    Ok(())
}

关键设计决策

  • trait 方法不使用 async：需要异步执行的 trait 方法使用 async_trait。
  • WASM 优先的工具：所有外部工具代码在带燃料与内存限制的沙箱 WASM 实例中运行。
  • 处处埋点：每个重要操作都记录 Prometheus 指标以便观测。
  • 两级缓存：L1（内存 DashMap）+ L2（sqlx + SQLite）提供快速键值存储。

沙箱：嵌入式与守护进程架构

WASM 沙箱有两种运行模式，由 Config.sandbox.use_sandboxd 控制：

嵌入式模式（use_sandboxd = false，默认）

┌───────────────┐     ExecuteTool     ┌─────────────────┐
│   gRPC Bridge  │ ──────────────────> │  WasmToolExecutor │
│               │ <────────────────── │  (wasmtime)      │
└───────────────┘     return result   └─────────────────┘
  • wasmtime 在 bridge 进程中内嵌运行。
  • 部署简单，无 IPC 开销。
  • OOM 风险：cranelift JIT 内存在进程退出前不会释放。
  • 适合开发与低吞吐场景。

守护进程模式（use_sandboxd = true）

┌───────────────┐     gRPC (IPC)     ┌──────────────────┐
│   gRPC Bridge  │ ──────────────────> │ sisyphus-sandboxd │
│               │ <────────────────── │  (wasmtime)       │
└───────────────┘     return result   └──────────────────┘
         │                                │
         │ 启动时生成子进程                │ 每次调用独立的 WASM
         │ 退出时回收                    │ 实例生命周期
         ▼                                ▼
   子进程池                       燃料门控执行

Bridge 启动时生成 sisyphus-sandboxd 作为受管子进程，优雅关闭时回收。通信通过本地 gRPC（tonic）通道进行，守护进程监听 127.0.0.1:0（临时端口）。

优势：

  • 进程级隔离：sandboxd 崩溃不会拖垮 bridge。
  • 内存隔离：每次 WASM 调用可在全新的守护进程进程中运行。
  • 独立扩展：守护进程可部署在单独的硬件上。
  • OOM 缓解：守护进程可在不中断 bridge 的情况下重启。

配置：

  • sandboxd_path：sisyphus-sandboxd 二进制路径，默认为 PATH 搜索。
  • 守护进程通过自己的 gRPC 服务接收 wasmtime 执行请求，使用与 ExecuteTool 类似的契约。

DAG 执行

Cognitive Loop

概述

认知循环（Cognitive Loop）是 Sisyphus 执行引擎的核心迭代过程。它遵循 预测 → 执行 → 反思 → 演进（predict → execute → reflect → evolve）的四步循环，持续优化 SOP 图的执行质量直至收敛。

Cognitive Loop v2

从 2026 年 7 月起，认知循环引入了三个新组件以提升效率、鲁棒性和探索能力。

AdaptiveDepthController

替代固定 max_iterations 上限，改用基于置信度（confidence）的自适应深度控制。

  • 每次迭代记录置信度，在滑动窗口（默认 3 次）上计算收敛速度（convergence velocity）。
  • 使用 ComplexityAnalyzer 根据图拓扑、目标复杂度和经验库计算初始迭代预算。
  • 满足以下任一条件时停止：达到目标置信度（默认 0.95）、收敛停滞（窗口内改进量 < 0.01）、达到硬上限（默认 30 次）。
  • 强制 min_iterations（默认 2）防止过早停止。

ParallelBranchPredictor

同时模拟多个变体 SOP 图，并选择最佳分支执行。

  • 对每个变体执行两类模拟：执行模拟（预测成功率、成本、稳定性）和逻辑模拟（检测逻辑缺陷）。
  • 综合评分公式：0.5 × success_probability + 0.3 × cost_efficiency + 0.2 × predicted_stability - logical_penalty
  • 通过 ExperienceBank 校准置信度，使历史成功数据影响分支选择。
  • 默认：max_branches = 3，concurrency = 3。

AnomalyDetector

在运行时监控每个节点的执行指标并标记异常。

  • 跟踪三类指标：燃料消耗（>2.0x 基线）、执行时长（>3.0x 基线，>5.0x 为高严重性）、错误率（>30%）。
  • 使用指数加权移动平均（EWMA，alpha = 0.3）进行基线追踪。
  • 产生 AnomalyReport，其中的 should_extra_reflect 标志触发额外的反思循环。
  • 集成于 StrategicManager，使循环能在执行过程中自我修正。

数据库后端

[cache] 中的 database_url 支持两种后端：

PostgreSQL / pgvector

用于带 ANN 索引的语义相似度搜索：

  1. 在 Postgres 服务器安装 vector 扩展
  2. 设置 database_url = "postgres://user:pass@host/sisyphus"
  3. 设置 enable_vectors = true 和 vector_dimension = 1536（或你的嵌入模型维度）
  4. SqlStore 连接时自动运行 CREATE EXTENSION IF NOT EXISTS vector

覆盖优先级

  1. 默认值（各子配置 Default 实现中硬编码）
  2. 配置文件（通过 SISYPHUS_CONFIG 环境变量或 Config::from_file() 指定路径）
  3. 环境变量（SISYPHUS_ 前缀，最高优先级）

性能

Sisyphus 包含多项性能优化。

流水线批处理

节点根据历史执行时间进行自适应批次执行：

  • 快速节点（<50ms）：较大批次（1.5x）
  • 慢速节点（>500ms）：较小批次（0.7x）
  • 中等节点：保持当前批次大小

输出去重缓存

OutputCache 存储内容哈希索引的结果，避免重复执行相同计算：

  • 1000 条目容量
  • 基于内容哈希（确定性）
  • 达到容量自动逐出

上下文压缩

大上下文值自动压缩：

  • 字符串超过阈值：截断并加标记
  • 对象超过 10 个键：仅保留前 10 个键

执行性能分析器

跟踪每个节点的执行指标：

  • 按节点类型的平均时长
  • 缓存命中率
  • 最慢节点列表

cargo bench -p sisyphus-core

性能调优

缓存调优

OutputCache 的逐出策略与容量可针对不同工作负载调优。

参数默认值说明建议
缓存容量1000逐出前的最大条目数重复工作负载时增大
上下文阈值4096触发压缩前的字节数内存受限时减小
批次基数4初始流水线批次大小高吞吐时增大

权衡：更大的缓存以减少重复执行为代价占用更多内存。通过性能分析器监控缓存命中率。命中率低于 60% 时考虑增大容量。超过 95% 时减小容量可释放内存且不影响性能。

Sandboxd 模式选择

沙箱守护进程（sandboxd）可运行在两种模式：

模式延迟隔离使用场景
嵌入式~50µs进程开发、可信工作负载
守护进程~500µs容器生产、不可信代码
  • 嵌入式在进程内实例化 Wasm 运行时。延迟最低，但无容器级隔离。适合开发与 CI。
  • 守护进程通过 gRPC 与单独的 sandboxd 进程通信。每次调用延迟更高，但提供容器级沙箱。

在 Config.tool_executor 中通过配置工具执行器切换模式。守护进程模式是生产部署的默认。

并发任务调优

认知循环支持可配置的并发，用于并行分支评估。

# config.toml
[cognitive_loop]
max_concurrent_tasks = 4      # ParallelBranchPredictor 中的并行分支
max_iterations = 30           # 认知迭代次数上限
convergence_threshold = 0.15  # 偏差低于此值时停止

调优指南：

  • max_concurrent_tasks：CPU 密集型工作负载设置为 CPU 核心数。I/O 密集（LLM 调用）时，更高值（8-16）可提升吞吐量。
  • max_iterations：更低的值降低最坏情况延迟。更高的值提升收敛质量。
  • convergence_threshold：更严格（更低）的阈值提升输出质量，但需要更多迭代。

使用 RUST_LOG=sisyphus_core=info 通过 tracing spans（predict、execute、reflect、evolve）监控认知循环性能。

评测套件

Sisyphus 通过 evals/ 目录对专业代理（Metis、Momus、Librarian、Scribe、SecurityOracle）进行量化能力评测。评测以 JSON 用例驱动，运行结果输出得分表。

运行方式

make eval            # 等价于 cargo run -p eval-runner
make eval-check      # 仅检查编译

评测器在 evals/runner.rs 中实现，自动加载 evals/<agent>/cases.json 下的全部用例，按代理分组执行，并汇总得分。

用例结构

每个代理目录下的 cases.json 是一组用例（Case）。字段如下：

字段类型说明
idstring用例唯一标识
agentstring目标代理：metis、momus、librarian、scribe、SecurityOracle
inputobject传入工具的参数（随代理而异）
expectedobject基准输出或关键组成
criteria[]array判据列表
metadataobject（可选）类别与难度（easy/medium/hard）

用例结构由 evals/schema.json（JSON Schema draft-07）定义。eval-runner 启动时会用该 schema 校验全部用例文件，不合规则立即报错退出，防止无效用例混入。

判据类型

每个 criteria 条目通过 check_type 选择验证方式：

类型说明示例 expected_value
keyword输出文本包含指定关键字## Context
regex输出文本匹配正则\[Core Conclusions\].*\[Detailed Evidence\]
json_schema输出 JSON 匹配子 schema{"type": "object", ...}
llm_judgeLLM 判官评估输出是否符合语义标准The decision must explicitly state ...

weight（默认 1.0）控制判据在用例总分中的占比。用例得分为通过的判据加权和除总权重，全部通过才算 PASS。

评测模式

EvalRunner 依据环境变量选择 LLM 客户端：

  • LLM_API_KEY=mock（默认）：使用内置 MockLlmClient，所有代理工具直接返回固定结构。此模式用于验证管线与结构，无真实智能，llm_judge 判据会按结构匹配。
  • 设置真实 LLM_API_KEY/LLM_ENDPOINT/LLM_MODEL：使用 DynamicLlmClient 调用真实模型，全量判据（含 llm_judge）按语义评估，得到真实能力得分。

基线报告

evals/capability_baseline_report.md 记录 2026-06-24 的初始基线（总体 0.86，47/57 通过）。每次重大代理提示词或工具变更后，应重新运行 make eval 并更新报告。

添加用例

  1. 确定目标代理与覆盖缺口，选择 evals/<agent>/cases.json 追加用例；
  2. 明确 check_type：结构固定用 keyword/regex，语义判断用 llm_judge，大对象校验用 json_schema；
  3. 运行 make eval-check 确认通过编译；
  4. 运行 make eval 确认新用例被加载并校验。
