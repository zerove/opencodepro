Sisyphus — Cognitive Computation Engine

Sisyphus — Cognitive Computation Engine

Sisyphus is a cognitive computation engine for building autonomous AI agents that plan, execute, and improve their behavior through a recursive observe–orient–decide–act (OODA) loop.

What It Does

At its core, Sisyphus takes a high-level goal (expressed in natural language) and:

  1. Synthesizes a Standard Operating Procedure (SOP) — a directed acyclic graph (DAG) of executable sub-steps.
  2. Executes the SOP in parallel across available nodes, respecting dependencies.
  3. Simulates outcomes via Monte Carlo tree search to predict success probability.
  4. Reflects on execution results — computing a deviation score between predicted and actual outcomes.
  5. Evolves the SOP — retrying failed nodes, increasing fuel budgets, or restructuring the graph.

This loop continues until the goal converges (deviation below threshold) or a maximum iteration limit is reached.

Why Sisyphus?

  • Self-improving: The engine learns from every execution, evolving its SOPs without human intervention.
  • Safe by design: WASM sandboxing for tool code execution with fuel limits and memory bounds.
  • Observable: Built-in Prometheus metrics for every cognitive operation.
  • Composable: Each crate is independent; use just the parts you need.

Project Status

Sisyphus is in active development (v0.1.0). The core cognitive loop is functional and tested, with WASM tool execution, multi-level caching, and Prometheus metrics integration.

Key Design Decisions

  • No async in trait methods: The system uses async_trait for trait methods that need async execution.
  • WASM-first tooling: All external tool code runs in sandboxed WASM instances with fuel and memory limits.
  • Metrics everywhere: Every significant operation records Prometheus metrics for observability.
  • Two-level cache: L1 (in-memory DashMap) + L2 (SQLite via sqlx) for fast key-value storage.

sisyphus-core — Kernel & Orchestration

The central crate that orchestrates the entire cognitive loop. It depends on all other crates.

Key Components

SisyphusKernel

The main entry point for the cognitive loop. Holds references to the SOP synthesizer, simulator, reflector, evolver, memory store, and WASM tool executor.

#![allow(unused)]
fn main() {
pub struct SisyphusKernel {
    pub intel: Arc<SisyphusIntel>,
    pub mem: Arc<dyn MemoryStore>,
    pub executor: Arc<WasmToolExecutor>,
}
}

CognitiveLoop::execute_goal()

The primary cognitive cycle:

  1. Synthesize: Convert natural-language goal into SOP graph via SisyphusIntel::synthesize_sop().
  2. Execute: Run the SOP graph using the DAG executor, respecting node dependencies.
  3. Simulate: Run Monte Carlo simulation over execution traces via StandardReflector::simulate_paths().
  4. Reflect: Compare predicted vs. actual outcomes via StandardReflector::reflect().
  5. Evolve: If deviation > threshold, mutate the SOP via StandardReflector::evolve().
  6. Loop: Repeat steps 2–5 until convergence or max iterations.

DagExecutor

Executes a SOPGraph with topological ordering. Nodes with zero in-degree execute in parallel via tokio::task::JoinSet. Results propagate through the graph via Arc<ExecutionContext> sharing.

CLI

The crate includes a binary integration_stress that runs an end-to-end in-process integration test.

sisyphus-types — Core Data Structures

Standalone crate (zero dependencies) providing the data model used by all other crates.

Key Types

SOPGraph

A directed acyclic graph (DAG) of nodes, using petgraph::graph::DiGraph. Each node is a SOPNode containing metadata like name, description, tool type, and required fuel.

#![allow(unused)]
fn main() {
pub struct SOPGraph {
    pub graph: DiGraph<SOPNode, f64>,
    pub metadata: SOPMetadata,
}
}

SOPNode

A single node in the SOP graph.

#![allow(unused)]
fn main() {
pub struct SOPNode {
    name: String,
    description: String,
    tool_type: String,
    fuel_budget: u64,
    max_retries: u32,
    retry_count: u32,
    timeout_ms: u64,
}
}

ExecutionContext

Thread-safe shared context for storing named values (String → serde_json::Value). Passed as Arc<ExecutionContext> through the DAG, enabling parallel node access.

ExecutionResult

Result of a single node execution, containing the output value, execution duration, and fuel consumed.

CognitiveReport

Full report from a cognitive loop iteration, including:

  • Channel trace with step-by-step reasoning
  • Reflection report with deviation scores
  • Simulation result with predicted success probability

Config

TOML-deserializable configuration struct for all Sisyphus components (fuel limits, pool sizes, paths, etc.).

sisyphus-intel — Cognition & Simulation

Provides the cognitive capabilities: Monte Carlo simulation, structured reflection, and SOP evolution.

Key Components

SisyphusIntel

Holds the synthesizer and reflector. Orchestrates goal synthesis and the cognitive loop’s reasoning steps.

StandardReflector

Three core responsibilities:

  1. Simulation (simulate_paths): Runs Monte Carlo over the SOP graph — samples execution paths from source to sink nodes, computing path probabilities and blended costs.

  2. Reflection (reflect): Compares simulated predictions against actual execution traces. Computes a deviation score (0.0 = perfect match) and generates structured improvement suggestions.

  3. Evolution (evolve): Mutates the SOP graph based on reflection output — adds retry wrappers around failed nodes, adjusts fuel budgets via AdaptiveFuelPricer, and restructures subgraphs as needed.

AdaptiveFuelPricer

Exponential backoff fuel pricer that increases fuel for nodes that ran out, and decreases it for nodes that consistently succeed.

MonteCarloSimulator

Core simulation engine using random path sampling through the DAG to estimate:

  • Success probability per path
  • Expected execution cost
  • Best path identification

sisyphus-mem — Memory & Caching

Two-level cache store for SOP execution history, intermediate results, and configuration.

Architecture

┌──────────┐     ┌──────────┐
│   L1     │     │   L2     │
│ DashMap  │────▶│  SQLite  │
│ (memory) │     │  (disk)  │
└──────────┘     └──────────┘
  • L1: In-memory DashMap<String, serde_json::Value> for sub-millisecond reads. No persistence.
  • L2: SQLite via sqlx for persistent storage. Fallback when L1 misses.

Write Strategy

Writes go to L2 (SQLite) first, then update L1. This ensures durability even if the process crashes before L1 sync.

Read Strategy

Reads check L1 first. On miss, query L2, and if found, populate L1 before returning.

Key Operations

OperationDescription
set(key, value)Write to L2 → update L1
get(key)Check L1 → check L2 → return
snapshot()Dump all entries into a Snapshot struct
restore(snapshot)Restore from a previously taken snapshot

sisyphus-sandbox — WASM Runtime

Provides a sandboxed WASM runtime for executing tool code safely within the cognitive loop.

Key Component: WasmToolExecutor

#![allow(unused)]
fn main() {
pub struct WasmToolExecutor {
    engine: Engine,
    module_cache: Arc<Mutex<HashMap<String, Module>>>,
}
}

Construction

WasmToolExecutor::new() creates a Wasmtime Engine with:

  • Pooling instance allocation: Pre-allocated memory pools for fast instantiation.
  • Memory limits: Max 1 MB memory per instance (max_memory_size(10 * 65536)).
  • Fuel metering: Configurable fuel limits to prevent runaway execution.

Execution Flow

  1. Load: Read WASM binary from the filesystem (path: wasm_tools/{tool_id}.wasm).
  2. Compile: Compile into a Wasmtime Module (with caching to avoid recompilation).
  3. Instantiate: Create an instance with fuel and memory limits.
  4. Call: Invoke the run export function with input bytes.
  5. Return: Return the result bytes or an error (fuel exhaustion, memory exhaustion, etc.).

Fuel System

Wasmtime’s fuel metering tracks WASM instruction consumption. When fuel runs out, execution is immediately aborted with a ResourceExhausted error, which the cognitive loop interprets as a signal to retry with more fuel.

Console Output Capture

The executor captures WASM module stdout/stderr via WasmtimeConsole and routes it through tracing.

sisyphus-bridge — Entry Point & API

The binary crate that ties all components together into a runnable application.

Entry Points

main.rs (Server)

A Tonic gRPC server that exposes the cognitive loop as a network service:

  • ExecuteGoal: Submit a natural-language goal path for execution. The bridge calls SisyphusKernel.execute_goal() and returns the cognitive report.
  • ExecuteSop: Execute a pre-synthesized SOP by ID, with optional evolution loop.

client.rs (CLI Client)

A gRPC client binary for interacting with the server:

cargo run --bin client -- execute-goal --goals /path/to/goal.json
cargo run --bin client -- sop --sop-id my_sop

stress_test.rs (Benchmark)

An in-process stress test that synthesizes and executes SOPs in a loop, measuring throughput and latency.

Configuration

The bridge reads configuration from TOML files and environment variables, constructing the sisyphus_types::Config struct and initializing all subsystems.

  • Standard Operating Procedure (SOP) — DAG representation of executable procedures
  • Cognitive Loop — The recursive observe–orient–decide–act cycle

Standard Operating Procedure (SOP)

An SOP is a directed acyclic graph (DAG) that represents a procedure to achieve a specific goal.

Structure

           ┌──────┐
           │ Goal │
           └──┬───┘
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
┌──────┐ ┌──────┐ ┌──────┐
│Node 1│ │Node 2│ │Node 3│
│ WASM │ │ WASM │ │ WASM │
└──┬───┘ └──────┘ └──┬───┘
   │                  │
   └──────┬───────────┘
          ▼
     ┌────────┐
     │ Result │
     └────────┘

Each node contains:

  • Name: Unique identifier within the SOP
  • Description: What this step does (used for synthesis and reflection)
  • Tool Type: Which WASM tool binary to invoke
  • Fuel Budget: WASM instruction limit for this node
  • Timeout: Maximum wall-clock time for execution
  • Retry Policy: Max retries and current retry count

Lifecycle

  1. Synthesize: The StandardReflector generates an SOP graph from a natural-language goal using the synthesizer module.
  2. Execute: The DagExecutor runs the SOP with topological ordering.
  3. Evolve: After reflection, the SOP may be mutated — new nodes added, fuel budgets adjusted, or subgraphs restructured.

Evolution Operations

OperationDescription
Retry wrapperWrap a failed node with retry logic
Fuel increaseBoost fuel budget for nodes that exhausted fuel
Subgraph restructureReorder or split nodes for better parallelism

Cognitive Loop

The recursive OODA-inspired cycle that drives Sisyphus’s self-improvement behavior.

Phases

1. SYNTHESIZE ─────────────────────────────┐
   │ Goal → SOP Graph                       │
   ▼                                        │
2. EXECUTE ──┐                              │
   │ SOP →    │ (loop back                  │
   │ Results  │  on evolve)                 │
   ▼          │                              │
3. SIMULATE   │                              │
   │ Traces → │                              │
   │ Predictions                             │
   ▼          │                              │
4. REFLECT    │                              │
   │ Actual vs│                              │
   │ Predicted│                              │
   ▼          │                              │
5. DECIDE     │                              │
   │ Converge?│                              │
   │          │                              │
   ├─ Yes ────┘                              │
   │   Return result                         │
   │                                          │
   └─ No ────────────────────────────────────┘
        Evolve SOP → loop to EXECUTE

Convergence

The loop terminates when one of these conditions is met:

  • Deviation threshold: The reflection deviation score drops below CONVERGENCE_THRESHOLD (typically 0.15).
  • Max iterations: The loop has executed MAX_COGNITIVE_ITERATIONS (default 10) times without converging.
  • No evolution: The evolver returns None, indicating no further improvements are possible.

Metrics

Each iteration records:

  • Iteration number and deviation score
  • Whether it converged
  • Duration of the iteration
  • Evolution actions taken (fuel changes, retry wrapper, etc.)

DAG Execution

Sisyphus executes SOP graphs using a parallel topological executor.

Algorithm

  1. Compute in-degrees for all nodes in the graph.
  2. Seed the ready set with nodes whose in-degree is zero.
  3. Spawn ready nodes concurrently via tokio::task::JoinSet.
  4. Collect results as they complete → decrement in-degree of downstream nodes.
  5. Add newly-ready nodes to the next batch.
  6. Repeat until all nodes complete or an error occurs.

Parallelism

Nodes with no dependency relationship execute simultaneously:

Time ─────────────────────────────────────►
┌──────┐  ┌──────┐  ┌──────┐
│Node A│  │Node B│  │Node C│  (parallel)
└──┬───┘  └──────┘  └──┬───┘
   │                    │
   └──────┬─────────────┘
          ▼
     ┌────────┐
     │Node D  │  (sequential — awaits A & C)
     └────────┘

Error Handling

  • If any node returns an error, the error is propagated up to the caller.
  • The cognitive loop catches node errors and evolves the SOP to add retry wrappers.
  • Cycle detection: If adding an edge creates a cycle, the operation is rejected with an error.

Fuel & Memory

Each node executes with its configured fuel budget and memory limit. Nodes that exceed limits are aborted with a descriptive error, which the cognitive loop uses to adjust future executions.
